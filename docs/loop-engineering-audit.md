# LOOP 工程现状审计

> 范围：本工作区（AIWorkSpace）作为「AI 编码工程骨架」在 LOOP 工程维度上的现状、缺口与补强条件。
> 性质：现状审计，不是规格，不产生 Requirement / Scenario，不进入 OpenSpec 变更流程。
> 基准：`AGENTS.md` §2 三层分工、§3 六条硬规则、§4 标准工作流、§9 已知边界。

## 1. 结论摘要

| 判断 | 结论 |
|---|---|
| 循环是否存在 | **存在且不可选**：只要有 harness（红 → 修 → 复验），循环就已经在跑 |
| 循环是否有界 | **部分有界**：工作单元有界（14 号闸门 + 归档终止），运行轮次无界 |
| 当前的「界」由谁提供 | **由人提供**：§4 第②步人工审阅放行 + 合并 main 前须审阅 |
| 工程化程度 | harness 强、LOOP 半、GRAPH 主动裁剪 |
| LOOP 是否必须 | **人在环时可延后；人离环时必须补**。详见第 9 节 |

一句话：**本项目不是没有 LOOP，而是把 LOOP 外包给了人。**

## 2. LOOP 工程的四件套

判定一个循环是否「工程化」，看它是否具备以下四件。缺任何一件，都只是「带验证器的 while(true)」。

| 要件 | 回答的问题 | 缺失后果 |
|---|---|---|
| 收敛判据 | 什么算完成 | 不知道什么时候该停 |
| 迭代预算 | 允许几轮「红 → 修」 | 用次数换绿灯 |
| 停滞检测 | 连续 N 轮无新证据时怎么办 | 在同一个坑里反复挖 |
| 失败上报 | 主动认输如何成为可执行动作 | 沉默消耗，等人发现 |

## 3. 已实现的 LOOP 能力

### 3.1 收敛判据（强）

| 信号 | 位置 | 含义 |
|---|---|---|
| `run-all.ps1` 退出码 0 | `harness/run-all.ps1` | 16 道闸门全部通过，任一道红即停 |
| 13 号集合相等 | `harness/checks/13-spec-evidence-check.ps1` | 每条 Scenario 都被显式分类，引用路径真实存在 |
| 14 号无超限 | `harness/checks/14-change-scope-check.ps1` | 在飞 change 粒度合规或持有未到期例外 |
| 归档完成 | `openspec archive` | change 移入 `archive/`，主规格同步，生命周期终止 |

特点：结论由退出码裁决，不由 AI 自评。`AGENTS.md` §3 明确「AI 的自我评价、代码行数、注释完整性都不构成证据」。

### 3.2 单轮判定的客观性（强）

- `harness/checks/03-static-guard.ps1` 拦截 `@Disabled`、`it.skip`、`describe.skip`、`xit`、`xdescribe`、注释断言、`TODO/FIXME/XXX`、`System.out`，且对「源码目录不存在」「源文件 0 个」直接 `exit 1`（fail-closed，拒绝在空目录上给绿灯）。
- CI 运行同一套 `run-all.ps1`，本地绿与远端绿不是两套标准。

### 3.3 工作单元粒度上限（中）

- 14 号闸门：单 change 能力 ≤ 2、tasks ≤ 30、scenarios ≤ 60；超限须 `scope-exception.md`，且 `Reason` / `RegisteredOn` / `Expires` 三字段完整、`Expires` 未到期。
- 它限制的是「一次装多少」，**不是**「修几轮」。粒度有界 ≠ 轮次有界。

### 3.4 证据棘轮（强）

- 13 号闸门对新增 Scenario 是棘轮：规格新增一条而账本未登记即判红，集合相等才算通过。
- 防止「为了让闸门变绿而补一条假证据」——`verified` 必须指向仓库中真实存在的 gate / test / e2e / runner。

### 3.5 生命周期终止（强）

- change 生命周期固定为 propose → apply → archive，归档即终点，不存在「永远在飞的 change」。
- 归档后 change 目录移入 `openspec/changes/archive/`，不可继续修改。

### 3.6 人工卡点作为隐式 LOOP（强，但不可自动化）

- `AGENTS.md` §4 明确：第②步「人类必须审阅放行」是整条链路里**唯一不可省略的人工节点**。
- 分支纪律：任何改动走独立分支，合并 main 前必须经用户审阅。
- **这两条是目前真正的「界」**：人决定了「这一轮够不够」「要不要继续改」。

### 3.7 归档与推送的收口习惯（中）

- 归档标签 `archive/<日期>-<change>` 与主规格同步落库，形成可追溯的时间线。
- 推送后以远端 ref 哈希核对，避免「本地绿≠远端绿」。

### 3.8 防伪造绿灯的四条静态红线（强）

- Java：`System.out`、`@Disabled`、`TODO` 占位。
- 前端：`it.skip` 类跳过写法、`TODO` 占位。
- 由真实事故驱动增补，不预先设想（§9）。

## 4. 未实现 / 部分实现的 LOOP 能力

### 4.1 轮次不可观测（最基础缺口）

| 项 | 现状 |
|---|---|
| 是否记录「第几轮」 | 否。轮次只存在于对话历史，会话压缩后丢失 |
| 是否记录「这轮有什么新证据」 | 否 |
| 后果 | 没有观测，迭代预算与停滞检测都无从校准 |
| 触发补强的信号 | 出现一次「复盘时说不清改了几轮、每轮依据是什么」 |

### 4.2 迭代预算缺失

| 项 | 现状 |
|---|---|
| 单 change 允许几轮「红 → 修」 | 未设上限 |
| 风险 | 用次数换绿灯：反复微调直到某次碰巧通过 |
| 缓解现状 | 03 号禁止跳过断言、13 号要求证据真实，堵住了「改测试让它绿」的捷径，但没有堵住「改代码直到碰巧绿」 |
| 触发补强的信号 | 单个 change 的修复轮次 ≥ 5，或同一闸门连续 3 轮红 |

### 4.3 停滞检测缺失

| 项 | 现状 |
|---|---|
| 连续 N 轮无新证据时是否强制停手 | 否 |
| 风险 | 在同一个坑里反复挖；本轮 13 号闸门缺陷的排障曾走十余轮诊断才定位到「PowerShell 单元素数组被展开为标量」 |
| 缓解现状 | AI 自觉 + 人追问 |
| 触发补强的信号 | 出现一次「改了多次仍停在同一个红，且每轮没有产生新证据」 |

### 4.4 失败上报缺失

| 项 | 现状 |
|---|---|
| 「我修不好了」是否是可执行动作 | 否。只能继续试或等人问 |
| 风险 | 沉默消耗；人离机时无人知晓进度停滞 |
| 缓解现状 | 阶段汇报（人工约定的沟通习惯），不是流程机制 |
| 触发补强的信号 | 出现一次「长时间无进展但没人被通知」 |

### 4.5 分支内的循环无节点

| 项 | 现状 |
|---|---|
| 分支内允许多少轮修改 | 无限制 |
| 合并前审阅能看到什么 | 最终 diff，看不到「中间磨了几轮、改过什么又被推翻」 |
| 风险 | 分支内「磨绿」后再一次性交审，审阅者无法判断过程质量 |
| 触发补强的信号 | 审阅时发现分支历史里有大量反复试错但最终 diff 很小 |

### 4.6 跨 change 的宏观循环不可见

| 项 | 现状 |
|---|---|
| 同一模块被连续多个 change 反复返工是否有信号 | 否 |
| 14 号只约束单个 change 的体积，不约束「同类 change 的重复出现」 |
| 风险 | 局部合规、整体返工 |
| 触发补强的信号 | 同一模块连续 3 个以上 change 涉及同一处修正 |

## 5. 为什么现在不补

依据 `AGENTS.md` §9：**护栏由真实事故驱动增补，不预先设想。**

预先加预算与检测的三个实际代价：

1. **维护成本**：每多一条规则，就要同步文档（07 号）、账本（13 号）、约定（11 号）。
2. **误伤正常多轮修复**：本轮 13 号缺陷的十余轮诊断是**必要的**，硬性预算会把它拦在半路。
3. **阈值没有真实数据校准**：3 轮还是 5 轮，只能由真实事故给出参考值。

## 6. 触发补强的客观信号

出现任意一条，即说明「无界」已经产生了实际代价，可以立项：

1. 同一闸门连续 3 轮红，且每轮没有产生新证据。
2. 单个 change 的「红 → 修」轮次达到 5 次。
3. 出现「先注释断言 / 先跳过，之后再补」的企图（未遂也算）。
4. 合并审阅时发现分支内已经反复修改多轮，但过程无人知晓。
5. 同一模块连续 3 个以上 change 涉及同一处修正。

## 7. 最小落地清单（触发后按此顺序）

顺序原则：**先能观测，再能停手，再能计量，最后能上报**。没有观测，预算与检测都无法校准。

| 顺序 | 动作 | 新增代码 | 落点 |
|---|---|---|---|
| 1 | 轮次观测：在 change 的 tasks.md 中记录「闸门红 → 修」的轮次与每轮根因 | 无 | 流程约定，写入技能 |
| 2 | 停滞检测：同一闸门连续 3 轮红且无新证据 → 停手输出根因分析 | 无 | `systematic-debugging` 技能加一条硬规则 |
| 3 | 迭代预算：同一 change 的修复轮次上限 | 有（改 14 号或新增闸门） | `harness/checks/` |
| 4 | 失败上报：主动认输的标准动作（当前状态 / 已排除项 / 需要什么支持） | 无 | `AGENTS.md` §3 增补一条 |

其中第 1、2、4 项零代码，只是把已有习惯写成硬规则；只有第 3 项需要动闸门。

## 8. 与 harness、GRAPH 的边界

| 层 | 回答的问题 | 本项目状态 |
|---|---|---|
| harness | 这一轮做对了吗 | 强：16 道闸门、CI 同源、证据棘轮 |
| LOOP | 循环什么时候停 | 半：只有收敛判据，无预算 / 停滞检测 / 上报 |
| GRAPH | 多节点怎么编排 | 默认串行单 agent；满足任一进入条件时按需并行 |

三条边界判断：

- **harness 越强，单轮信号越准，对 LOOP 的依赖越低**，但不能降到零。
- **LOOP 是正确性的终点，GRAPH 是吞吐量的起点**。二者服务不同目标，不是「更高级」。
- **GRAPH 的进入条件**是四个客观触发之一：任务可分解且子任务独立、单上下文装不下、需要角色互检、吞吐成为瓶颈。当前四条都未触发，因此默认仍走串行；任一条件成立即可按需拆分并行，不视为违规。

## 9. 专项回答：LOOP 工程是必须的吗

### 9.1 循环不可选，界是必须的

只要有 harness，「红 → 修」的循环就已经存在。问题不是「要不要循环」，而是「要不要给已有的循环加界」。**无界的循环不叫 LOOP，叫无限重试。**

### 9.2 界可以由人承担，但只在人在场时成立

本项目当前的界由两条人工节点提供：

- §4 第②步：人类审阅 proposal 后才允许实施。
- 合并纪律：任何改动合并 main 前必须经用户审阅。

这两条是真实有效的界——每一次「执行合并」都是人给出的一次收敛裁决。但它们有一个前提：**人在场。**

### 9.3 因此「必须」的准确表述是

> **人在环时，LOOP 工程可以延后；人离环时，LOOP 工程就是必须的。**

判断依据不是「项目是否高级」，而是三个具体问题：

1. 人是否会在循环中途离开？（是 → 需要）
2. 单次循环是否可能变长到人无法逐轮跟踪？（是 → 需要）
3. 是否已经出现「磨绿」或「长时间无进展」？（是 → 必须补）

### 9.4 对本项目的结论

- 当前没有「磨绿」事故，按 §9 不预加闸门。
- 但「人离环」是既定事实（协作习惯已明确记录：用户不会一直守在电脑前）。
- 因此建议：**不做预算闸门，先把第 7 节里零代码的三条（观测、停滞检测、上报）写进技能与契约**，等真实事故出现再考虑动 14 号。

这不是「以后再说」，而是「用零成本先把最脆弱的一环补上」——因为一旦人不在场，现在的界就等于不存在。
