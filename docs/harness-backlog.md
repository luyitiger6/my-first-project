## 2. 待优化项

### 2.1 闸门缺少「因何而生」记录（优先度最高）

**现状**：16 个脚本普遍写清了「守什么」（例如 06 号头注释那句「这道闸门守的从来不是某个迁移工具，而是『表真的建对了』」），但没有一道记录「因哪次事故、哪个 change 而生」。

**后果**：未来判断某道闸门「还需不需要」时无从下手。闸门越多，越没人敢删——因为没人知道删掉会怎样。

**建议最小动作**：每个脚本头部加一行来源，例如：

```powershell
# 因：posts 契约加字段后前后端漂移未被发现（2026-xx / change: add-post-interactions）
```

**成本**：一行注释。**价值**：为将来的「该不该删」保留判断依据。

**状态（2026-11-09）**：已落地。16 道闸门全部在头注释补了「因」行，格式为「因：<拦什么失效>（<引入日期> 提交 <hash>）」，来源逐条取自 `git log --diff-filter=A` 的首次提交，不编造事故；02/05/09/10 是行注释脚本，其余是块注释。块注释内的「因」行紧贴闸门标题，便于肉眼扫。补「因」时发现 06 号注释早已乱码，根因与处置见 §2.9。

### 2.2 缺少闸门退出机制

**现状**：AGENTS.md §8 只定义「怎么加」，未定义「怎么删」。

**后果**：闸门只增不减，是单向棘轮。

**待定**：删除条件如何判定（例如「对应能力已下线 + 连续 N 次归档未触发」）暂不预设，等真的需要时再定。这符合 §9「不预先设想」。

### 2.3 06 号四组清单靠人工维护（成本最高）

**现状**：加一张表要同时改 Tables / Indexes / Constraints / CreatedAt 四组清单；漏改会「永久失明且不报错」——AGENTS.md §9 已记录该风险。

**可选方向**：从 DDL 脚本自动提取结构，与期望清单比对反差集，替代人工维护四组清单。

**代价**：改造 06 号本身有成本；自动提取对生成列、CHECK 约束的解析不一定完整，可能引入新的假绿灯。

**结论**：先不做。等它真的因为「漏登记」出过一次事，再改。

### 2.4 注册表型闸门的登记遗漏风险

**现状**：10 号靠 `$contractPairs` 人工登记，新增模块忘了加就永久漏扫。

**可选方向**：扫描 `backend/.../web/*/dto/` 自动发现，与 `frontend/lib/contracts/*.ts` 交叉比对。

**代价**：会失去「显式声明」的好处——并非所有 dto 目录都该纳入比对（如内部传输对象、未对外开放的中间载体）。

**结论**：先不做，保持显式登记。

### 2.5 02 号的既有测试依赖真实库「干净」状态（2026-11-08 完整验收命中）

**现象**：`PostServiceTest.keysetPagingDoesNotRepeatOrSkip` 断言两页合计恰为 3 条。库里只要多出 1 条其它已发布帖子（如 6.1 联调产物），断言就失败——测试只造自己的 3 条，未隔离库里已有的数据。

**后果**：任何往 `wanderchain.posts` 留下已发布数据的联调或造数动作，都会让 02 号出现与本次改动无关的假红。本次处置是软删除那条联调帖子，属绕开而非修复。

**建议最小动作**：测试自带数据隔离（夹具先清空或断言只按自己的标识集合过滤），或把断言改为「两页合计 ≥ 3 且不重复不遗漏自己的 3 条」。**成本**：一处用例改写。另开 `fix/` 分支，不随本 change 携带。

**状态（2026-11-09）**：`add-direct-messages` 8.2 完整验收再次命中同一用例（dev 库实有 2 篇已发布帖），已随该 change 就地改写断言——沿游标翻到本用例三篇都出现、跨页不重复不遗漏、插队帖不落后页；断言数由 5 增至 6，不触 15 号测试弱化闸门。本节可关闭。

### 2.6 02 号的既有测试对时间边界敏感（2026-11-08 完整验收命中）

**现象**：`PasswordResetTest.resetCodeSharesTheDailyQuotaWithRegisterCode` 断言两次 429 的 `Retry-After` 严格相等；该值是「距次日零点的秒数」，两次请求恰好跨过一秒边界时差 1 即失败（实测 29069 vs 29068）。

**后果**：在秒边界附近的窗口内跑 02 号会随机假红，与代码改动无关；本次重跑即过。

**建议最小动作**：断言改容差（判 `|差| ≤ 1`），或改为只比较「同一秒内发起」的哨兵口径。另开 `fix/` 分支，不随本 change 携带。

### 2.7 本地 dev server 用后台管道启动会进入病态空转（2026-11-09 命中）

**现象**：用后台 shell（stdout 接管道、无消费者）启动 `npm run dev` 后，进程 16 分钟累计烧掉 210 秒 CPU（约 22% 单核），但 `.next/dev` 连续 4 分钟零写入——在消耗资源，没有任何产出。同期请求时通时不通，浏览器里表现为首页反复重载、登录按钮时有时无。

**后果**：把进程病态误当成业务 bug 去查，在「改代码」和「查环境」之间来回试，属于最典型的空循环；用户侧看到的是功能坏了。

**建议最小动作**：本地启动一律把输出重定向到文件（`cmd /c npm run dev > %TEMP%\wc-3000.log 2>&1`），不要用后台管道；启动后立刻取「无请求时的 CPU 增量」与「日志行增量」两个数，任一非零即视为病态进程，直接杀掉重启，不看业务。

**成本**：一条启动命令 + 两个读数。**价值**：把「进程是否健康」从感觉变成可读的数。

### 2.8 06 号闸门 DROP DATABASE 会清掉本地既有账号（2026-11-09 命中）

**现象**：跑一次 06 号建表闸门后，`wanderchain.accounts` 只剩当次造数产生的两个 E2E 账号，用户本人账号消失，此后所有登录持续 401、`/me` 永远 401。根因见 §4「不把闸门拆成并行执行」中已描述的行为：06 号对 `wanderchain` 执行 `DROP DATABASE ... CREATE DATABASE`。

**后果**：本地联调的身份被闸门抹掉，且很难当场联想到是闸门干的；用户侧表现为「账号登不上、获取不到用户」，排查会先怀疑认证逻辑。

**建议最小动作**：三选一——(a) 06 号在 DROP 前把既有 `accounts` / `posts` 行导出到临时表或文件，建表后回灌；(b) 06 号只在专门的 gate schema 上 DROP，不碰 `wanderchain`；(c) 什么都不改，但在 AGENTS.md §7「只查建表」一行显式标注「本闸门会清空 wanderchain 数据」。

**成本**：一次脚本改造，或一行文档标注。**价值**：把「跑闸门」和「丢数据」解绑。

### 2.9 Turbopack 监听根被推断到整个工作区（2026-11-09 命中）

**现象**：`next dev` 启动日志告警 `We detected multiple lockfiles and selected the directory of D:\my-first-project\package-lock.json as the root directory`，Turbopack 的 workspace root 落在工作区根而不是 `frontend/`。

**后果**：`backend/target`、根 `node_modules`、`.qoder/` 等目录都落在监听范围内，后端一编译就可能触发前端重编译与页面重载，同时拉高空闲 CPU。

**建议最小动作**：`frontend/next.config.ts` 增加 `turbopack.root` 钉在 `frontend` 自身。另开 `fix/` 分支，不随本 change 携带。

**成本**：三行配置。**价值**：把监听范围收回到真正需要的地方。
### 2.10 共享 Redis 的长 TTL 计数键 × 06 重建库的自增 id 复用（2026-11-09 完整验收命中）

**现象**：`CredentialsNormalizationTest.shortPasswordIsRejectedBeforePasswordIsCompared` 断言「连续 4 次密码错误还不该触发图形码」，实际触发。根因不在用例：账户维度失败计数落在共享 Redis，键是 `wc:login:fail:acct:{accounts 自增 id}`、TTL 30 天；06 号每轮 DROP 重建 `wanderchain`，`accounts` 自增 id 回到低位被下一轮复用，新种账户抽到一个「上一轮留下过失败计数」的 id——残留 1 加本次 4 次等于 5，正好越过 `fail-threshold: 5`。实测库里残留 44 个这类键（值全为 1，id 覆盖 30–1147），而 accounts 表只有 id 1、2。

**后果**：任何「重建库 + 复用低位 id」的完整验收都会让账户维度限流用例假红，失败集合与本次改动无关；排查时容易误判为产品缺陷。

**本次处置**：在 `saveActive` 种下账户后调 `throttle.clearAccountFailures(saved.id())`，与 `LoginThrottleChainIntegrationTest` 的既有处理一致；未改产品代码。

**建议最小动作**：把「种账户后清账户维度计数」抽成所有涉及登录限流的用例共用的夹具基类，消除逐类复制；或让测试库的自增起始值避开历史 id 段。**成本**：一处夹具抽取。另开 `fix/` 分支，不随本 change 携带。

### 2.11 06 号建表闸门会重建 schema，本地既有数据被清空（2026-11-09 完整验收命中）

**现象**：`06-schema-check.ps1` 对 `ai_chat_gate` 与 `wanderchain` 执行 `DROP DATABASE ... CREATE DATABASE`，跑完两个库的业务数据全部归零——accounts、posts、attractions、dm_conversations、dm_messages 一并丢失。

**后果**：不备份就跑完整验收，本地账号与联调数据全丢；用户账号消失后表现为登录持续 401，且损失不可逆。

**本次处置**：跑前 `mysqldump --databases wanderchain ai_chat_gate --single-transaction --no-tablespaces --routines --triggers --events` 备份到 `%TEMP%\wc-backup-20261109-173042.sql`，跑完用同一 dump 恢复并核对行数（accounts 2 / posts 2 / attractions 13 / dm_conversations 1 / dm_messages 7 / auth_sessions 38，两库 10 + 4 张表）。

**建议最小动作**：06 号在 DROP 前自动 dump 到 `%TEMP%`，或给 `run-all.ps1` 加 `-BackupDb` 开关；至少让 06 号开头打印「本闸门会清空下列库，请先备份」。**成本**：约 10 行。另开 `fix/` 分支，不随本 change 携带。

### 2.12 以默认编码重写 .ps1 会把中文注释静默变成乱码（2026-11-09 补「因」行时发现）

**现象**：`06-schema-check.ps1` 的第 3–7 行与 10 处分节注释全是 `寤鸿〃闂搁棬` 这类双重编码乱码，但闸门照常 PASS。`git log -S '寤鸿'` 定位到引入提交 `52a8b32`（2026-10-30 posts 归档），该提交的 diff 首行是 `-# 06-schema-check.ps1` → `+# 06-schema-check.ps1`：整个文件被无 BOM 的 UTF-8 重写为带 BOM，中文在这一步被按 GBK 解码后再存为 UTF-8。

**后果**：注释失真但不报警；若被破坏的是参与匹配的中文字符串或正则，闸门会静默失效而不是报错。乱码还会沿 `git blame` 传给下一个人，且容易被当成无意义装饰而无人修。

**本次处置**：按行号用正确原文（`git show 52a8b32^:harness/checks/06-schema-check.ps1` 的父版本）恢复 15 行注释，保留 UTF-8 BOM 与 CRLF，并补「因」行；`Parser::ParseFile` 语法 0 错、可疑字符计数 0、`git diff` 除注释外无变化。

**建议最小动作**：写 .ps1 时用 `[IO.File]::WriteAllText($p, $t, [Text.UTF8Encoding]::new($true))` 显式指定编码，不依赖 `Set-Content` / `Out-File` 的默认值；提交前对 `harness/` 扫一次乱码特征（`閳|閿|瀵ら缚|寤鸿|鈥斺`）。**成本**：一条排查命令；若要固化成 16 号编码闸门，也符合 §3「由真实事故驱动」。

## 3. 新增闸门的判定原则（供未来参考）

1. **由真实事故驱动**：先有「假绿灯逃逸」的事实，再加闸门（AGENTS.md §9）。
2. **判据不是数量，是「能不能一句话说清它拦什么」**：能说清的 100 道是清单，说不清的 1 道是黑箱。
3. **优先做成全局扫描型**：一次写好永久生效，不需要随模块登记。
4. **新增时必须同步三处**：`<!-- harness-checks: -->` 标记、§6 目录地图、§7 命令速查——07 号会强制前两项。

## 4. 明确不做的

- **不引入「闸门预算」或「数量上限」**：当前 16 道没有造成任何实际负担，预设上限属于 §9 禁止的「预先设想」。
- **不为闸门增加「分级 / 标签」体系**：`run-all.ps1` 的扁平顺序 + 文件名编号已经够用。
- **不把闸门拆成并行执行**：除了早停语义，更硬的原因是资源共享——`06-schema-check.ps1` 第 174 行对 `wanderchain` 与 `ai_chat_gate` 执行 `DROP DATABASE ... CREATE DATABASE`，与 02 号的测试库是同一个；01 与 02 争同一个 `backend/target/`；04 的 `npm ci` 与 05 的工作区整目录复制争 `node_modules`。并行会让闸门互相制造假红，比慢更糟。
- **CI 里提速走 job 级，不走闸门级**：把 02 与 04 拆成两个 job，各自 `services:` 起独立 MySQL / Redis——GitHub 的 job 跑在不同 runner 上、互不共享网络，这一步省不掉；代价是 checkout 与装依赖各来一遍。实测基线见 §1——02 占 105.2 s、04 占 53.9 s、其余 14 道合计约 50 s，总约 210 s；离 §5 的 5 分钟触发线还差一半，因此暂不拆。真要拆也只值得拆这两道，其余 14 道加起来约 50 s，拆了反而多付启动成本。
- **并行边界：前端可并行，后端串行**：前端三个功能各落独立目录（`components/posts/` / `components/attractions/` / `app/search/`），dev server 单进程服务全部页面，vitest 按文件并行且不依赖真实后端，所以开发与测试都能并行；公共面只有 `package.json`、`layout.tsx`、`globals.css`、`lib/contracts/` 几处，开工前划分即可。后端不行：`schema.sql` 是单文件装所有表、`accounts` 被全部外键依赖、`mvn test` 连真库且共享夹具与唯一索引、`target/` 每轮争用——写代码勉强能并行，但验证环节必然撞，所以整体按串行处理。
- **万一将来真要多实例，隔离粒度在库不在表**：MySQL 按 schema、Redis 按 db 编号（现用 db 3）、RabbitMQ 按 vhost、Kafka 按 topic 前缀、MinIO 按 bucket；容器数应恒为 1，不要按「中间件数 × 并发数」扩容器。两点前提：`application.yml` 与 06 号的 `$authDb` 现在写死 `wanderchain`；Redis 的 db 隔离拦不住 `FLUSHALL`。本条只是备查，不代表当前需要并行。

## 5. 触发补强的信号

出现以下任一情况时，回头处理本文档：

1. 因为漏登记（06 或 10 号）导致一次真实假绿灯逃逸。
2. 完整验收时间超过 5 分钟且瓶颈出现在检查型闸门而非编译测试。
3. 有人问「这道闸门是干什么的」而现有文档答不上来。
4. 闸门数量达到 25 道。
