## 简介
本前端应用基于 React 19 与 Next.js 16，采用现代的前端工程化方案：TypeScript 类型安全、Vitest 单元测试、Playwright 端到端测试、Next.js App Router 路由与 API 路由、Docker 容器化部署。应用已从简单的 Todo 待办功能扩展为完整的 wanderchain 旅行平台，包含城市筛选、编辑推荐、热门帖子、热门景点、AI 助手入口、用户认证等丰富功能。

**重大更新** 应用现已实现完整的认证系统，采用服务端会话管理而非本地存储。认证令牌通过 HttpOnly Cookie 传输，前端不直接访问令牌，确保更高的安全性。认证系统支持两步验证码注册、图形验证码验证、错误码驱动的差异化提示等高级功能。同时新增了完整的帖子 Feed 功能，支持排序切换、无限滚动和互动统计展示。

应用采用清晰的组件化设计，通过 HomeRepository 接口抽象数据源，支持 Mock 数据与真实 API 的无缝切换。所有网络请求通过 `lib/api.ts` 暴露的函数进行封装，配合同源代理路由避免跨域问题并统一错误处理。

该文档面向开发者与维护者，既提供高层架构说明，也深入到组件实现、数据层设计、状态管理、API 客户端封装、代理路由、类型定义、测试与构建配置等技术细节，帮助读者快速理解并扩展系统。

## 核心架构与设计模式
wanderchain 旅行平台采用以下核心设计模式：

### 数据层抽象
通过 `HomeRepository` 接口定义数据契约，使用 `mockRepository` 实现 Mock 数据，未来可轻松切换到真实 API 实现而不影响组件层。

### 认证上下文模式
使用 React Context 管理用户认证状态，`AuthProvider` 提供全局认证状态和操作方法，`useAuth` Hook 供组件访问认证信息。**更新** 认证系统现在完全基于服务端会话，不再依赖本地存储。

### 组件化设计
每个功能模块独立成组件，如 CitySwitcher、EditorPicks、HotPosts 等，组件间通过 props 传递数据和回调。遵循「组件三件套」约定：同名同目录的 `.tsx`、`.module.css`、`.test.tsx` 三个文件。

### 状态管理
使用 React Hooks 进行轻量状态管理，`useSectionData` Hook 统一管理区块级数据加载状态。

### 类型安全
完整的 TypeScript 类型定义，包括 CitySlug、EditorPick、Post、Attraction、AuthUser 等业务类型，以及认证相关的类型定义。

```mermaid

Repository --> MockImpl["Mock 实现<br/>mockRepository"]
```

## 认证系统与用户管理
wanderchain 旅行平台实现了完整的认证系统，采用服务端会话管理，确保更高的安全性和一致性。

### 认证架构
认证系统采用 Provider-Consumer 模式，完全基于服务端会话：
- **AuthProvider**：提供全局认证状态和操作方法的 Context Provider
- **useAuth Hook**：供组件访问认证状态的自定义 Hook
- **Auth API 客户端**：封装所有认证相关的 API 调用，处理错误码分流
- **HttpOnly Cookie**：令牌存储在安全的 HttpOnly Cookie 中，前端无法直接访问

### 核心特性
- **服务端会话管理**：通过 `GET /api/auth/me` 判定当前登录状态
- **两步验证码注册**：先提交图形验证码答案换发邮箱注册码，再提交邮箱注册码完成注册
- **图形验证码验证**：登录时根据后端要求动态显示图形验证码
- **错误码驱动**：根据后端返回的错误码显示不同的用户友好提示
- **限流保护**：自动处理速率限制，显示等待时间

### 用户界面
- **登录页面** (`/login`)：用户登录表单，支持邮箱密码验证和图形验证码
- **注册页面** (`/register`)：新用户注册，包含用户名、邮箱、密码确认和两步验证码流程
- **账户菜单**：已登录用户的下拉菜单，显示用户信息和登出选项

### 安全特性
- **令牌安全**：认证令牌仅存在于 HttpOnly Cookie，前端无法读取
- **无敏感数据存储**：不在 localStorage 或 sessionStorage 中存储任何敏感信息
- **错误信息脱敏**：不泄露账户是否存在等敏感信息

```mermaid
AuthApi --> Backend["后端服务<br/>HttpOnly Cookie"]
Backend --> AuthProvider["会话状态同步"]
```

## API 客户端与代理路由
前端通过 Next.js 应用服务器提供静态资源与页面，同时使用 API 路由作为同源代理，把 `/api/todos` 的请求转发到后端服务。浏览器只与前端同域通信，避免跨域配置复杂性。

### 认证 API 客户端
`lib/auth/auth-api.ts` 定义了认证相关的 API 方法：
- `fetchCaptcha()`：获取图形验证码
- `requestRegisterCode()`：请求邮箱注册码
- `registerAccount()`：完成用户注册
- `login()`：用户登录
- `fetchCurrentAccount()`：获取当前用户信息
- `logout()`：用户登出

内部使用 `fetch` 发起同源请求，统一处理非 2xx 响应并抛出错误，组件侧捕获后显示友好提示。

### 通用 API 客户端
`lib/api.ts` 定义了 `Todo` 类型与三个 API 方法：
- `getTodos()`：获取待办列表
- `createTodo(title)`：新增待办
- `completeTodo(id)`：完成指定待办

### 同源代理路由
`app/api/[...path]/route.ts` 实现了通用代理路由：
- 从环境变量 `BACKEND_URL` 或默认值读取后端地址
- 将 Next.js 接收到的请求路径与方法、查询串、请求头与请求体转发到后端
- 透传上游响应的状态码与内容类型
- 当后端不可达时返回 502 错误

## 故障排查
常见问题与定位思路：

### 旅行平台相关问题
- **城市筛选无效**：检查 `parseCity` 函数是否正确解析 URL 查询参数，确认 `CitySlug` 类型定义是否包含目标城市
- **数据加载失败**：检查 `useSectionData` Hook 的错误处理逻辑，确认 `mockRepository` 的实现是否正确
- **空状态显示异常**：检查各组件的空状态判断逻辑，确认数据格式是否符合预期

### 响应式设计问题
针对新的响应式设计的故障排查：

- **热门景点网格布局异常**：检查 CSS 媒体查询断点是否正确，确认 480px、720px、1080px 断点生效
- **图片加载问题**：检查 `sizes` 属性配置是否正确，确认响应式图片在不同屏幕尺寸下的加载行为
- **移动端显示异常**：检查移动端断点下的样式覆盖是否正确应用

### 认证系统相关问题
- **登录失败**：检查 `auth-api.ts` 中的错误处理逻辑，确认后端返回的错误码是否正确映射
- **会话丢失**：检查后端服务是否正常，确认 HttpOnly Cookie 是否正确设置
- **注册失败**：检查两步验证码流程，确认图形验证码和邮箱验证码的处理逻辑
- **图形验证码不显示**：检查 `fetchCaptcha` 函数的调用时机，确认注册流程的第一步是否正确执行

### 帖子 Feed 功能问题
- **排序切换无效**：检查 `parseSortBy` 函数是否正确解析 URL 参数
- **无限滚动不工作**：检查 IntersectionObserver 的配置和哨兵元素的可见性
- **帖子卡片显示异常**：检查 PostCardStats 组件的统计数据渲染逻辑

### Todo 应用相关问题
- **后端不可达**：代理路由在捕获异常时返回 502，检查 `BACKEND_URL` 环境变量是否正确配置，确认后端服务是否启动。
- **请求失败提示**：API 客户端对非 2xx 响应抛出错误，组件会显示错误消息；检查后端返回的状态码与响应体。
- **列表未更新**：确认 `createTodo` 与 `completeTodo` 返回值结构与 `Todo` 类型一致，确保组件能就地更新状态。

### Playwright E2E 测试相关问题
- **测试无法启动**：检查端口是否被占用，确认 `scripts/e2e-run.mjs` 的端口探测逻辑
- **浏览器连接失败**：检查 Playwright 浏览器安装情况，确认 `E2E_CHANNEL` 环境变量配置
- **测试超时**：检查网络请求和页面加载时间，调整 `timeout` 和 `actionTimeout` 配置
- **截图缺失**：确认失败截图目录权限，检查 `failureScreenshot` fixture 是否正确配置

### 测试相关问题
- **组件测试失败**：需要 mock 相应的数据层或 API 函数；检查用例中的断言是否与实现一致。
- **代理路由测试失败**：需在 node 环境并 mock `fetch`，检查用例中的断言是否与实现一致。
