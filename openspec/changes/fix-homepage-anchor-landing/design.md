# Design

## Context

首页三个内容区块（编辑推荐、热门帖子、热门景点）是客户端组件：首屏渲染加载态占位（173–180px），`useSectionData` 拿到 Mock 数据后替换为真实列表（618–1095px）。区块 `<section id>` 在加载态就已存在，所以浏览器/Next 的锚点滚动会在占位布局上完成；随后上方内容变高，目标区块被推向视口下方。1440×900 实测偏移 1215px。

直接访问 `/#hot-posts` 实测正确落位（目标距视口顶 0px），说明缺陷出在「导航后仍在变化的布局」而不是锚点本身。

实施后 E2E 暴露第二个边界：`/#hot-attractions` 是文档最后一个区块，实测 `scrollY = maxScroll = 2996`、区块顶部距视口顶 317px（偏差 248px，占视口 27.6%）。滚动已到尽头，不是补偿失效。

## Goals

- 带锚点进入首页时，无论区块处于加载态还是就绪态，最终都停在目标区块。
- 不改变任何既有契约：数据层、区块加载三态、搜索页 SSR、首页加载态语义全部保持。
- 不与用户抢滚动条。

## Decisions

### 决策 1：客户端补偿滚动，而不是服务端直出区块数据

在首页挂载一个客户端组件：有 hash 时，把目标区块按「吸顶头部实际高度」向下对齐；同时用 `ResizeObserver` 观察主内容区，布局每次变化都重新对齐，直到连续若干帧无变化或到达超时。

- **理由**：缺陷的根因是「布局在导航后才稳定」，补偿点必须与布局变化同源；服务端直出虽能一次性消除抖动，但会删掉加载态、改动既有区块数据契约与相关规格（U2 骨架、三态展示），爆炸半径远大于收益。
- **被否**：服务端一次性取数并直出（会破坏加载态规格与组件契约）；纯 CSS `scroll-margin-top`/`scroll-padding-top`（只能解决吸顶遮挡，解决不了加载后位移）；全局 `scroll-behavior: smooth`（与 `prefers-reduced-motion` 降级冲突，且会让 E2E 落位断言变得不稳定）。

### 决策 2：对齐偏移用运行时测量的头部高度，不写死常量

吸顶头部是 `position: sticky`，桌面单行 68px，窄屏换行后会更高。补偿时读取头部实际 `offsetHeight` 作为偏移，而不是把 68px 写进 CSS 或 JS 常量。

- **理由**：写死常量在 320px 断点会让区块标题被头部压住一半，属于典型的「单点修改跨文件重复配置值」缺陷。

### 决策 3：让位条件写成显式事件

监听 `wheel`、`touchstart`、`keydown`（方向键/翻页/空格/Home/End）三类输入，一旦触发就停止本次校正；观察器最长存活 3 秒，之后无论是否稳定都不再干预。

- **理由**：补偿的本质是「修正浏览器算错的落点」，不是接管滚动；超过 3 秒仍不稳定的布局已经不属于锚点问题的范畴。

### 决策 4：页尾锚点接受滚动尽头，不追加空白

`/#hot-attractions` 之后只剩页脚（126px），文档只剩那么多可滚距离，把区块顶到头部下沿在物理上不可达。判据改为「偏差 < 10% 视口高，或已停在 maxScroll 且标题可见」；不为对齐而在页面底部补空白。

- **理由**：页尾锚点的用户目标是「看到这块内容」，全部区块标题与正文已在视口内；为凑齐 248px 而在页脚后留白会制造无意义空白，且会把约束变成「页面高度服从锚点」。
- **被否**：在 `main` 底部加 spacer（制造空白、影响所有页尾布局）；只降低判定到「区块进入视口」（会把页尾例外漏给中段锚点）。

## Risks

- Mock 数据是同步 Promise，真实接入网络请求后加载时间变长：超时上限内仍能校正，超时后由浏览器原生锚点行为兜底，不会比现状更差。
- 页尾例外依赖「已到 maxScroll」判定：若未来在首页底部新增内容，`#hot-attractions` 会自然变成可达锚点，现有断言无需修改即可继续通过。
- 无 hash 的首页多挂一个空转组件：组件在无 hash 时立即返回，不注册观察器。
- `ResizeObserver` 在极老浏览器缺失：做能力判断，缺失时只执行一次对齐。
