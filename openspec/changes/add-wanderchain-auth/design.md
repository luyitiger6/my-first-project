# Design

## Context

后端当前只有 Todo 一个内存实现的模块，没有任何认证相关代码。前端存在一套 Mock 认证（`frontend/lib/auth/mock-auth.ts`）：账号存 localStorage、密码明文、令牌为 `alg: none` 的假 JWT，并在生产构建下主动抛错拒绝运行——它证明了「接口形状」这件事已经有人想过，但服务端从未真正签发过身份。

本变更的前提按最新决定重置：**后端会连接数据库，也会连接其他中间件**。因此本设计不再假设「运行期无外部依赖」，也不再以历史遗留的迁移基线为约束——持久化结构在本变更内重新定义。

动机见 `proposal.md`，行为契约见 `specs/wanderchain-auth/spec.md`。本文只回答「怎么实现才不违背那些契约」。

## Goals / Non-Goals

**Goals:**

- 让状态机的三个状态在代码结构上**不可绕过**：状态只能通过显式迁移方法改变。
- 让「响应不含凭证字段」由**测试**证明，而不是由代码评审的口头承诺保证。
- 让 `403` 只在「密码已经验对」之后出现，使状态码映射不构成账户枚举手段；登录失败只触发限流，不制造不可登录的账户状态。
- 令牌可即时吊销，与「注销与改密立刻生效」的契约一致。

**Non-Goals:**

- 不设计刷新令牌、多设备会话管理界面、密码找回流程。
- 不做角色与权限模型（`admin` 解锁动作只作为迁移触发者存在，权限体系另行立项）。
- 不改前端 Mock 认证；接入真实接口是后续变更。
- 不在本变更内决定邮件服务商与缓存中间件的具体产品。

## Decisions

### D1 端点集合

| 方法 | 路径 | 成功码 | 说明 |
|---|---|---|---|
| `GET` | `/api/auth/captcha` | `200` | 返回 `captchaId` 与图形码；答案摘要入缓存，短 TTL |
| `POST` | `/api/auth/register-code` | `202` | 校验图形码后向邮箱投递注册码；已注册邮箱同形返回但不投递 |
| `POST` | `/api/auth/register` | `200` | 比对注册码，建立 `active` 账户并以 `Set-Cookie` 下发令牌 |
| `POST` | `/api/auth/password-reset-code` | `202` | 校验图形码后投递重置码；未注册邮箱同形返回但不投递 |
| `POST` | `/api/auth/password-reset` | `200` | 比对重置码并设置新密码；成功后全部旧令牌失效 |
| `POST` | `/api/auth/login` | `200` | 状态码由账户状态决定；成功时以 `Set-Cookie` 下发令牌；`429` 来自来源限流，与账户无关 |
| `POST` | `/api/auth/logout` | `204` | 吊销当前 `jti` 并清除认证 cookie |
| `GET` | `/api/auth/me` | `200` | 从 cookie 读取令牌；非 `active` 一律 `401` |
| `DELETE` | `/api/auth/account` | `204` | 注销，账户转 `deleted` |

`register-code` 与 `password-reset-code` 都是 `202`：它们只表示「请求已被受理」，不表示「码已发出」——已存在/未注册的邮箱也走同一分支，这正是防枚举的表达方式。`register` 是 `200`，因为它确实创建了账户并签发了令牌。`captcha` 与 `register-code` 分开而非合并，是为了让「谁能触发发信」由图形码这一道门槛单独控制，也让两层码各自的一次性与过期可以分开断言。

### D2 令牌用 JWT，但保留服务端校验点

用户选定 JWT。契约里的「账户离开 `active` 后既有令牌立即失效」与纯无状态 JWT 冲突，因此 JWT 只承担**身份载荷与签名**，时效性由服务端校验点保证：

```
签发   HS256 签名，载荷含 sub(publicId) / ver(账户令牌版本) / jti / iat / exp
校验   1. 验签与过期
       2. 查 auth_sessions：jti 未被吊销（登出、注销时写入）
       3. 查账户：status = active 且 ver 与载荷一致（注销与重置密码时版本自增，全部旧令牌作废）
```

- **代价（必须说清）**：JWT 省掉的是「令牌明文落库」，没有省掉那次查询——每个受保护请求仍要读一次会话与账户状态。换来的是后续服务可先离线验签再决定是否回查。反正每次都得回查，refresh token 那套「短 access + 轮换」的收益就只剩「泄露后暴露窗口更小」，而那点收益已被即时吊销兑现大半。
- **替代方案**：不透明令牌（一条记录代替两份校验，更简单）。用户明确选 JWT，此处保留记录便于日后回看。
- **有效期**：绝对 7 天，不滑动续期，`/me` 不续期。从 8 小时改为 7 天是随传输方式一并定的：存内存时 8 小时与 7 天都是幻觉（F5 就掉），换成 cookie 后 8 小时就成了硬伤（用户隔天打开必重登）。

**令牌放 cookie，不是 `Authorization` 头**：

```
下发   Set-Cookie: wc_session=<jwt>; HttpOnly; SameSite=Lax; Path=/; Max-Age=604800
读取   受保护请求从该 cookie 取令牌；不读 Authorization 头
登出   同名 cookie 置空 + Max-Age=0
CSRF   SameSite=Lax 挡掉跨站 POST；另加 Origin 校验做纵深防御
```

- 选 cookie 而不是内存：内存方案下 F5 就掉登录，要修就得同时引入 refresh（多一套轮换、复用检测、多标签页竞态）。cookie 把这个复杂度直接省掉。
- 选 cookie 而不是 localStorage：localStorage 对 JS 完全开放，一个 XSS 就能把 7 天会话完整拷走。`HttpOnly` 让令牌对脚本不可见。
- `SameSite=Lax` 已阻绝跨站的 `POST`/`DELETE`（浏览器根本不带 cookie），因此 CSRF 在技术上几乎不成立；Origin 校验是第二道，防止日后有人把 `SameSite` 改成 `None` 或引入子域发布时静默失去防护。
- 代价：cookie 对纯 API 客户端（将来的 App、第三方）不友好，到时另开 Bearer 路径，两者可共存；且 `Secure` 在本地 HTTP 开发环境需按 profile 关掉，这是配置项不是默认值。

### D3 登录判定顺序：先凭证，后状态

```
POST /api/auth/login
  |
  +-- 0. 来源维度限流：同 IP/设备在窗口内失败超上限 --> 429 + Retry-After（不比对密码）
  |
  +-- 1. 按邮箱查账户（无论存在与否，都执行一次等价耗时的哈希校验）
  |        不存在 --> 401（与密码错误同体）
  |
  +-- 2. 校验密码
  |        不匹配 --> 401（与上一步完全相同的响应体）
  |
  +-- 3. 已匹配，按状态分派
           active            --> 200 + 令牌
           email_unverified  --> 403
           deleted           --> 401（刻意复用凭证错误的响应体）
```

**为什么顺序不能反**：若先判状态，攻击者用任意密码探测即可从 `403` 读出「该邮箱存在且未验证」，邮箱枚举成本降到一次请求。先验密码则 `403` 只在「密码也是对的」时出现，攻击者已经拥有账户访问权，泄漏不再有价值。

**为什么 `deleted` 用 `401` 而不是 `410`**：`410 Gone` 会明确告知「这个账户刚被删除」，反而暴露注销行为。复用 `401` 让「已注销」与「密码错」在状态码、错误码、文案三个维度完全一致，这一点必须写成契约测试的断言，否则后人极易把它「修正」成更语义化的状态码。

**实现约束**：第 1 步必须对不存在的账户也走一次哈希校验（固定 dummy hash），否则响应时间会重新变成枚举信道。

**限流参数（替代账户锁定）**：账户维度连续失败 5 次后要求图形码；来源维度同来源在 10 分钟内失败 20 次返回 `429`，`Retry-After` 60 秒。一次成功登录将账户维度计数清零。

- 为什么不用锁定：锁定把防爆破的成本转嫁给合法用户，而攻击者用 5 次错误密码就能锁死任意已知邮箱。C 端产品的做法是限流 + 图形码，账户本身永不因登录失败而失效。
- 为什么账户维度计数放缓存：账户不再有「锁定状态」需要持久化，计数只需短期跨实例一致，缓存足够；数据库里多一列失败计数只会诱使后人把它重新实现成锁定。
- 阈值走外部配置：本地与自动化测试用小阈值（如 2 次）验证「要求图形码」与「返回 429」两条分支，否则没人会去触发它们。
- 为什么账户维度不给时间惩罚（实施 5.4 时删掉了原定的「递增的等待」）：它与本节下面「`Retry-After` 给短值而非指数攀升」的理由是同一件事，只是换了个入口；而且被惩罚的恰好是那个正被撞库的账户主人——把攻击成本转嫁给受害者，正是取消账户锁定的初衷。达阈值后必过图形码已经把撞库从脚本降为半人工，边际收益远不抵新增的计数公式、封顶值与测试。若日后发现图形码被机器破解，正确做法是提高码的强度或引入人工审核，而不是回到时间惩罚。

**登录入参**：`captchaId` + `captchaAnswer` 在未触发阈值时可省略；触发阈值后缺失或错误一律 `400` + `CAPTCHA_INVALID`，不进行密码比对。字段可选而非新增一个「预检」端点，一是避免客户端多一次往返，二是避免预检端点自己变成探测工具。

**来源怎么取（本项目特定）**：浏览器请求先到 Next.js 的 `/api/[...path]/route.ts` 再转发给后端，后端 `getRemoteAddr()` 看到的是 Next server 的地址。因此：

- 后端只信任「已登记代理层」的转发头，取它追加的那一跳。**实施 5.9 时确认：当前拓扑连这一跳也拿不到**——Next 的 Route Handler 没有客户端地址（`NextRequest.ip` 仅 Vercel 可用），`route.ts` 只转发 content-type 与 accept，所以 `wanderchain.auth.trusted-proxies` 落成空列表。此时每个请求都归入「未知来源」，与下面第三条是同一种 fail-closed 行为，且不会因登记错误而直信转发头；待前后端之间接入会追加 `X-Forwarded-For` 的 nginx / ALB，只需登记它的出口地址，代码不改（修正理由：原句把「前端代理一层」当成已经会追加可信跳，实际它拿不到地址，按原文实现会让人误以为生产上真的按 IP 分桶了）；
- 直达请求自带的 `X-Forwarded-For` 一律不采信，否则伪造一个 header 就能无限刷新额度；
- 取不到可信地址时归入单一「未知来源」桶，与任何真实 IP 不共享额度——宁可让这些请求彼此挤在一个桶里，也不能让它们绕过限流；
- IPv6 按 `/64` 聚合，否则一个用户手握 2^64 个地址等于没有限流。

来源计数不区分账户：同一 IP 轮流试 100 个邮箱就是撞库，不应因为「每个账户只失败一次」而免于限流。本次只覆盖登录失败；发码维度的来源限流（防拿我们当邮件轰炸机）登记为 Q18，后续补。

### D4 三态在代码里是一个受控枚举，不是字符串

领域层用枚举承载状态，迁移只能通过具名方法发生（`verify()`、`delete()`），且方法内部先校验当前状态是否允许该迁移，不允许即抛领域异常。禁止任何地方直接 `setStatus(...)`——字符串直写会让「未定义迁移被拒绝」这条 Scenario 无法被测试。

数据库列仍为 `VARCHAR + CHECK`，CHECK 枚举三值，与领域枚举一一对应；这是「代码可绕过」与「数据库可绕过」两条防线的最后一层。

`locked` 在校准阶段被删除：它的作用已由 D3 的双维度限流与图形码承担，而它带来的「可被他人锁死」这个面无法靠调参数消除。

`email_unverified` 保留为合法枚举值，但本变更内**不可达也不可离开**：没有任何端点会置入它，它也没有登出入口（登录 403 拿不到令牌，故注销走不通）。旧版状态机里那条 `email_unverified --本人注销-->` 边已被删除——声明一条永远走不到的边比不写更糟，它会让实现者去写一段死代码。对该状态只有两件事可做：用测试夹具造出来验「登录返回 403 且状态不变」；以及用一个端点清单断言证明没有入口。若日后引入改绑邮箱，那个变更必须同时交付验证出口。

### D5 敏感字段靠全局响应包装收口，覆盖范围先只做用户信息接口

```
领域对象        不提供 hash 的公开读方法；密码仅在凭证校验内部使用
    |
响应类型        独立的 record DTO，与领域对象无继承/复制关系
    |
全局响应包装    所有响应经统一类型出站，端点无法自行拼装响应体
    |
契约测试        针对 /me：字段路径 + 白名单比对 + 值扫描
```

覆盖范围由用户明确限定为「用户信息接口的响应」：

- 本变更只对 `GET /api/auth/me` 建立字段白名单与断言，其余八个端点暂不做逐字段断言。
- 兜底靠全局响应包装这一个出站收口：新增端点时若绕过包装类型，本身就是一个可被发现的偏差，而不是靠人记住「千万别返回密码哈希」。
- 其他敏感字段（手机号、内部自增 id、IP 等）的防护范围后续变更再定。

仍然保留的硬断言（其余端点为已知缺口，已在待决项登记）：

1. `/me` 响应递归展开字段路径，与显式白名单取差集，非空即失败。
2. 从持久化层取该账户的密码哈希，断言其字面值不出现在 `/me` 响应原文中。

不新增独立 Harness 闸门：这些断言作为普通单元/契约测试随 `02-test` 一起执行，符合「护栏按真实事故增补」的既有约定。静态正则扫描 DTO 字段名看似便宜，但会误伤注释与测试夹具，收益不抵成本。

### D6 密码与验证码的哈希形态

- **密码**：bcrypt（cost 12）。盐内嵌在哈希串里，因此**不存在独立的 salt 列**——「响应禁止返回 salt」的结构性落地方式是「根本没有这个字段」，而不是在 DTO 里删掉它。
- **验证码**：6 位数字熵很低，必须用 HMAC-SHA256（服务端密钥）而非裸 SHA 存储，避免彩虹表；同时绑定接收邮箱，使 A 的注册码无法用于 B。
- **图形码**：4 位字符，答案与 `captchaId` 存缓存，TTL 2 分钟，一次性，答错即作废换新。
- **邮箱注册码**：TTL 300 秒（5 分钟），一次性，比对失败上限 5 次，重发冷却 60 秒。取 5 分钟而非短信惯用的 60 秒，是因为两者链路长度不同：短信秒到，邮件要经过投递、网关、客户端拉取。给邮箱码套短信时长，等于把链路延迟转嫁给用户。全部配置化，不硬编码在业务分支里。
- **重置码**：与注册码共用同一段实现（同一 TTL、同一一次性语义、同一冷却与配额），但**缓存键按用途分段**（`wc:code:register:` / `wc:code:reset:`），只是验证通过后的去向不同（改密码 vs 建账户）。不另写一套，是因为两套码的参数一旦分叉，就必然会有一套没人维护。（本条在实施到 tasks 7.1 时修正：原文写的是「同一缓存键前缀」，按此实现会让一枚注册码同时满足重置码的比对——它不需要被「转换」，本身就是重置凭证。当下侥幸不可利用，只是因为两条链路的投递判据恰好互斥：注册码只寄给「无 `active` 账户」的邮箱，重置码只寄给「有 `active` 账户」的邮箱。互斥是两条独立判断的副产品，不是不变量；任一条放宽（例如将来允许给未验证邮箱补发注册码），注册码立刻变成重置凭证。分段的成本是一个常量，而这类问题一旦存在就没有低成本的兜底，故取分段。）
- **重发冷却键跨用途共用**（`wc:cooldown:email:`）：spec 的冷却约束写在「同一邮箱」而不是「同一邮箱的同一类码」上，按用途各记一份的话，连发注册码与重置码就能在 60 秒内寄出两封，冷却名存实亡。日配额同理，本来就是单一键。
- **邮箱日配额**：每邮箱每自然日 5 封，注册码与重置码合并计数；键为「邮箱摘要 + 日期」，不含明文。取 5 而非更大值：正常用户注册最多重发 2–3 次、找回 1–2 次，5 封足够，再大只是给滥用留空间。用自然日而非滚动 24 小时，是因为「每天 N 次」若实现成滚动窗口，用户永远不知道要等到什么时候；自然日边界才能让 `Retry-After` 给出一个确定时刻。
- **为什么配额在投递决策之前比对**：若先判断「该邮箱会不会收到信」再查配额，则已注册邮箱请求注册码（本就不投递）永远绕开限制——而攻击者恰恰会拿自己的邮箱反复刷这类请求。代价是「不会收到信的请求也计入配额」，这是故意的：宁可浪费攻击者的额度，不让它免费试探。
- **验证成功即删**：比对通过后在同一次处理内 `DEL` 该键，不等 TTL 自然到期。等它过期意味着多一个 5 分钟的可重放窗口，而删一次的成本是零。
- **存活时间与冷却的关系**：TTL 300 秒远长于冷却 60 秒，因此用户可以在旧码未到期时重发，旧码此时被主动删除——「只有最新一个码有效」不依赖 TTL 恰好到期。

### D7 持久化与中间件的必需边界

| 依赖 | 用途 | 必需性 |
|---|---|---|
| 关系型数据库 | 账户、会话与吊销记录 | 必需，认证无法无状态化 |
| 共享缓存（Redis） | 图形码、注册码、重置码、重发冷却、邮箱发码日配额、登录失败计数与来源限流窗口 | 必需——验证码、配额与限流计数存不住，注册链路与防爆破都失效 |
| 邮件投递通道 | 注册码外发 | 必需（本变更为模拟实现，见 D8） |

账户维度的失败计数与来源维度的限流窗口**都放共享缓存**：它们只为限流服务，不参与任何状态判定，缓存丢失只意味着限流暂时放宽，不会造成数据错误。反过来，把它们写进账户行会诱使后人把它重新实现成锁定。

持久化结构建在 `wanderchain` 库（本产品专属，与 `ai_chat_gate` 分属两个库），不复用历史迁移的既有表——`ai_chat_gate` 里的 `users` 属于 AI 会话项目，它的 `status` 取值域（`active`/`disabled`）与本模块的状态机不是一回事，混用会让同一张表承载两套互斥语义：

```
accounts       账户主体：邮箱、密码哈希、状态、令牌版本、注销时间
auth_sessions  会话与吊销记录：账户外键、jti、过期时间、吊销时间（JWT 不落明文，只留吊销集合）
```

邮箱的唯一性必须只对未注销账户生效：软删除下 `UNIQUE(email, deleted_at)` 会因未删除行的 `deleted_at` 全为 `NULL` 而彻底失效（InnoDB 把 `NULL` 视为互不相等），必须用生成列把「有效性」编码进唯一键，并在建表校验中断言「插入两条相同有效邮箱必定失败」。

图形码与注册码**不进数据库**，只在缓存里活 2 分钟/5 分钟。把它们落库会得到一屋子过期数据，却换不来任何正确性。

### D8 投递通道本变更用模拟发码程序

端口保留，实现只做一个模拟发码程序：验证码写入进程内 outbox 或投递记录表，由测试与开发期工具读取，不发真实邮件、不依赖网络。

三条护栏：

- 模拟实现的明文码 MUST NOT 通过任何 HTTP 响应暴露。**不提供「读验证码」的接口**——那会直接违反「响应禁含 verification_code」，调试时从测试夹具或数据库读取。
- 模拟实现只在非生产 profile 生效；生产 profile 下若没有真实发信实现，启动即失败，避免模拟件被当成真件发到线上。
- 端口签名不因模拟实现而变形，接真实邮件服务时只换实现，领域层与接入层零改动。

### D9 图形验证码的实现边界

- 服务端用 JDK 自带的 `BufferedImage` 手绘 4 位字符图，返回 base64，不引入图形验证码第三方组件——为一张图加一个依赖不划算。
- **可读性优先于防机器强度**（用户明确要求不要搞得太复杂）：不加重度扭曲、不堆干扰线，字符间留够间距、前景与背景对比度拉高。用「答错即作废 + 一次性」控制刷取成本，而不是靠把人也能绕过的难度。
- 看不清就刷新：每次 `GET /api/auth/captcha` 都生成新的 `captchaId`，与既有图形码并存、各自在存活时间内独立可校验。**为什么不是「旧的同时作废」**（本条在实施到 tasks 4.6 时修正）：该端点是纯无状态的，请求里没有任何字段能说明「这是刚刚刷新页面的那个人」，服务端无从知道该作废哪一张；真要做就得下发 cookie 记住「当前 captchaId」，为一个收益接近零的约束引入服务端会话状态——旧码同样需要正确答案、同样 2 分钟过期、同样一次性，强制作废挡不住任何实际攻击，却会让两个标签页互相作废对方的图形码。刷取的真正成本在「一次性 + 答错即作废 + 邮箱冷却 + 日配额」，不在「同时只许有一张」。**刷新是前端局部行为**——只替换图形元素与隐藏字段，不重新加载页面，服务端只需保证该端点可重复调用且不影响已发出的邮箱注册码。
- `captchaId` 是随机 UUID，**不携带邮箱**。若把邮箱编进 captchaId，图形码就变成「该邮箱正在注册」的旁路信号。
- 图形码有三个用途：换注册码、换重置码、以及登录连续失败后的强制校验。它从不参与提交类请求（注册提交只认注册码，重置提交只认重置码），两层职责不重叠。

### D10 运行期依赖的落地位置（本机环境事实）

复用本机既有实例，不新建容器。端点与隔离方式属于环境事实而非产品契约，因此不进 spec：

| 依赖 | 端点 | 隔离方式 | 凭据来源 |
|---|---|---|---|
| MySQL 8 | `127.0.0.1:8806` | 本产品专属 schema `wanderchain`；`ai_chat_gate` 留给 AI 会话项目、`green-note` 是他人业务库，均不混用 | 未设环境变量时从 8806 容器环境变量读取，与 `06-schema-check` 同一约定 |
| Redis 7 | `127.0.0.1:6606` | 独立 database index（默认 3）+ 统一键前缀 `wc:` | 同上，从 6606 容器环境变量读取 |

三点理由：

- **复用而非新建**：`06-schema-check` 已在 8806 上验证过建表。再起一个 MySQL，会让「闸门验证的库」与「应用连接的库」不是同一个——那是最没意义的绿灯。6606 与 8806 同属一个 compose 项目，成对使用省掉一套生命周期管理。
- **Redis 必须换 db index**：6606 上已有其它项目的键，共用 db 0 时一次 `FLUSHDB` 或一个键名撞车就变成跨项目故障，且排查时看不出边界。键前缀 `wc:` 仍然必需——Redis Cluster 不支持多 db，将来若换 Cluster，前缀是唯一还成立的那层隔离。
- **凭据不进工件**：这些文件要进 git。密码只以环境变量名出现，取值由运行环境提供。

配套闸门：Redis 不可达时注册与登录 MUST 整体失败（见 tasks 1.3）。为不让「Redis 挂了」变成运行时才发现的事，新增 `09-redis-check`，与 `06-schema-check` 对称——只检查连通与 db index、不写业务键、不建容器。

### D11 技术选型（六项，均未被既有规格或代码绑定）

`pom.xml` 第 45 行有一句明文注释：「只作为迁移工具使用：不引入运行期 flyway-core / DataSource / JPA」。本变更推翻其中两条（引入 JPA、引入启动建表），理由记录在此——否则后人只会看到结果，不知道当初为何这么定。

| 项 | 选型 | 与既有决定的关系 | 理由 |
|---|---|---|---|
| 持久层 | Spring Data JPA | 推翻「不引入 JPA」 | 本模块只有「按邮箱查」「按 `jti` 查」两类查询，无复杂 SQL；`@DataJpaTest` 直接可用。MyBatis 的 SQL 可控优势在此用不上，却要多一批 XML |
| 建表方式 | `schema.sql` + `spring.sql.init.mode=always`，启动时幂等执行 | 推翻「不引入运行期建表能力」，并放弃 Flyway | 本项目不做迁移：库里没有需要保住的数据，改结构直接 drop 重建。Flyway 的全部价值在「演进时保住已有数据」，无数据可保时它是纯负担。但手写 DDL 仍必需——`active_email` 生成列与具名 CHECK 是 1.1 的核心断言，JPA 的 `ddl-auto` 生成不出来 |
| Redis 客户端 | Spring Data Redis（Lettuce） | 新增 | Boot 默认带 Lettuce，线程安全且异步；`StringRedisTemplate` 已够用，不必自管连接 |
| JWT | jjwt 0.12 | 新增 | 只需 HS256 签发与验签；nimbus 的优势在多算法与 JWKS，本模块用不到 |
| 密码哈希 | `spring-security-crypto` | 新增（仅此一个 jar） | 含 `BCryptPasswordEncoder`，且**不触发 Security 自动配置** |
| 认证装配 | 不引 `spring-boot-starter-security` | 保留「不引入 Spring Security」 | 引入即默认得到表单登录页、HTTP Basic、CSRF、session 持久化、全请求认证、`/logout`，六项都要显式关掉；用 `HandlerInterceptor` 更可控 |

**放弃 Flyway 的连带处理**：`06-flyway.ps1` 改名为 `06-schema-check.ps1`，职责不变——它守的从来不是 Flyway，而是「表真的建对了」（表名、索引名、约束名、两个生成列、`created_at`、重复执行无副作用）。执行器从 `flyway:migrate` 换成 mysql 客户端。原 `V1__init_ai_chat.sql` 搬到 `db/ai-chat/schema.sql`，由该闸门在 `ai_chat_gate` 上执行，AI 会话那四张表与已归档的 `database-baseline` 能力因此原封不动。

**为什么不用 Security 的默认能力**：它的默认配置是围绕 form-login 与 session 设计的。真正白拿的只有安全响应头一项，其余五项都要覆盖；最直接的后果是既有的 `/api/todos` 被默认拦截，`02-test` 里 Todo 的测试当场变红。

**将来的授权需求怎么办**：社区帖子需要作者/管理员权限时，那属于授权而非认证。到那时迁移成本确实比现在高，但现在的成本同样真实——先多花半天关掉六项默认行为，并把一套还不存在的授权模型提前锁定。等那份需求出现时再选，判断依据比现在充分。

**配置缺失必须让启动失败（实测结论，不是假设）**：`@ConfigurationProperties` + record + `@NotBlank` 拦不住缺失的环境变量。Spring Boot 的 Binder 用 `PropertySourcesPlaceholdersResolver`，其内部 `PropertyPlaceholderHelper` 默认 `ignoreUnresolvablePlaceholders = true`——解析不出的 `${WANDERCHAIN_JWT_SECRET}` 会被**原样当作字符串值**绑定，`@NotBlank` 见到的只是非空文本，于是缺密钥应用照样启动，直到签发令牌时才炸。`@Value` 走的是 `PropertySourcesPlaceholderConfigurer`（默认不忽略），所以这个差异不是直觉能推出来的。对策：在 `AuthProperties` 紧凑构造器中显式检查值里是否还残留 `${`，命中即抛异常并点明该设哪个环境变量；`AuthPropertiesBindingTest` 用 4 条 `ApplicationContextRunner` 断言钉住这个行为（完整配置可绑定、缺 `session-ttl` 失败、缺 `jwt-secret` 失败、占位符未解析失败）。

**测试直连真库**（用户定）：`mvn test` 直连 `127.0.0.1:8806` 与 `127.0.0.1:6606`，不用 H2 或嵌入式 Redis。理由是 1.1 的核心断言「插入两条相同有效邮箱必定失败」依赖 MySQL 的生成列与唯一索引语义，H2 不保证同样行为，用它测等于没测。代价是 `02-test` 从此要求两个实例可达。

## Risks / Trade-offs

- **`403` 仍暴露「账户存在且未验证」** → 已用「密码校验先行」把可利用性压到零；但若未来出现「忘记密码 + 未验证提示」组合，会重新打开枚举面，届时需专门设计。
- **每请求一次会话表查询** → 换取即时吊销能力。若压测显示该查询成为热点，可加进程内短 TTL 缓存，但失效窗口必须小于契约允许的延迟。
- **验证码 6 位数字可爆破** → 依靠失败上限 + 冷却 + 两层码分离限制；若改为邮箱内链接（更高熵），需同步修改注册链路的入参契约。
- **邮箱码取 300 秒而非短信惯用的 60 秒** → 短信链路短、邮箱链路长（投递 + 网关 + 客户端拉取），套用短信时长会把延迟转嫁给用户。放宽到 5 分钟后，剩余风险是「旧码在重发后仍存活」，已用主动删除消除，不依赖 TTL。
- **图形码挡不住定向人工攻击** → 它只提高脚本成本，不是安全边界。真正的防线是「已注册邮箱不投递」，使攻击者永远拿不到能走完注册的码。
- **响应白名单会让开发变慢** → 这是有意为之：任何新增对外字段都必须显式登记，代价换来的是「凭证字段泄漏」这类事故在 CI 阶段被拦住。
- **取消账户锁定后爆破面变大** → 防线从「锁账户」改为「双维度限流 + 失败后强制图形码」。代价由「受害者被锁」转成「攻击者被限速」；若实测发现某个来源仍在大量试探，应上调来源维度阈值或加网关层封禁，而不是恢复账户锁定。
- **成功率驱动的限流可能误伤** → 同一 NAT 后的大量用户在来源维度共用计数，可能被一起限速。因此来源维度阈值必须远大于单账户阈值，且 `Retry-After` 给短值（60 秒）而非指数攀升。
- **日配额可被用来延误他人找回密码** → 攻击者过图形码后可耗尽某邮箱当日额度，使其当天收不到重置码。危害限于延迟（不能夺号，受害者仍可用旧密码登录），而图形码把自动化成本抬到人工级别。所以额度取 5 而非 1，给受害者留冗余。
- **`getRemoteAddr` 拿到的是代理地址** → 这是本项目最容易踩的坑：不解析可信代理链就全站共用一个桶（一人爆破全体受牵连），直信 `X-Forwarded-For` 又能被一个 header 绕过。两种错法都能跑通、测试也能绿，只有读代码的人能发现，因此必须有「伪造转发头不扩容」「未知来源单独计数」两条断言守着。
- **cookie 方案把 CSRF 防线集中到了一个属性上** → `SameSite=Lax` 一旦被改成 `None`（常见于“为了跨子域”这种需求）CSRF 就静默失效，不会报错也不会掉测试。缓解：Origin 校验作为第二道，且 spec 里把「两者皆缺失时拒绝」写成契约。
- **7 天且不滑动意味着过期不可感** → 用户不会在过期前得到提示，第 8 天点击任何写操作才掉登录，若当时有未保存内容就会丢。前端应在临近过期时提示，但那是前端变更，不在本变更内。
- **多实例下的时钟漂移** → 所有时间以应用生成的 UTC 时间写入，不使用数据库 `CURRENT_TIMESTAMP` 参与业务判断，避免实例与数据库时区不一致造成限流窗口与令牌过期判定错乱。
- **与其它项目共用同一套 MySQL/Redis 实例** → 共用带来的不是隔离，是「别人一次 `FLUSHDB` 或误删 schema 就打到你」。缓解：MySQL 用独立 schema、Redis 用独立 db index 加前缀、`09-redis-check` 每次验收都确认端点和 db index 没漂移。真正需要独立时（并发量或合规要求上来）再拆，而不是现在就为它付运维成本。

## Migration Plan

1. 先落持久化结构（`schema.sql` 建账户表与会话表 + 状态 CHECK），不加任何业务逻辑，确认重复执行无副作用。
2. 接入领域状态机与哈希、令牌签发，用内存仓储跑通全部 Scenario。
3. 换成数据库仓储，跑同一批契约测试，验证两种实现行为一致。
4. 邮件投递端口接上模拟通道，本地跑通「取图形码 → 换注册码 → 注册 → 登录」全链路。
5. 回滚：本变更不改动任何既有模块，回滚等于移除新增端点与新增表；无数据迁移，无兼容包袱。

### 本轮已定（用户答复）

- **首批范围**：auth 核心全套——注册（图形码 + 邮箱注册码）、登录 + 状态机；不含社区模块，不含全站响应包装改造。
- **令牌形态**：JWT，配套服务端校验点（见 D2）；有效期见下条「令牌传输与续期」。
- **验证方式**：注册验证用邮箱验证码，不用邮箱链接；注册成功即返回令牌完成首次自动登录。（链接方案因「网关预取消耗 token」与「email_unverified 无其他出口会锁死账户」被否。）
- **注册验证码链路**：注册页图形码 → 校验通过后投递邮箱注册码 → 注册码在 Redis 最多存活 5 分钟、验证成功即删 → 注册提交时与缓存比对；注册即 `active`（见 D1、D6、D9）。
- **邮件投递**：本变更用模拟发码程序，不接真实邮件服务（见 D8）。
- **注销后邮箱**：允许同一邮箱重新注册为新账户，旧账户行保持 `deleted`。
- **Q1**：由注册流程重构消解——图形码换注册码、注册即 `active`，验证票据与验证/重发两个端点一并取消。
- **账户锁定**：取消 `locked` 状态与 `423`——用户判定本项目是面向公众的产品而非内部系统，不应锁用户；改为账户维度（连续失败后要求图形码）与来源维度（超阈 429）双限流。
- **密码找回**：纳入本变更，复用图形码 + 邮箱重置码链路；重置成功使全部旧令牌失效。
- **令牌传输与续期**：令牌放 `HttpOnly` + `SameSite=Lax` cookie，响应体不含令牌；有效期绝对 7 天不滑动；不做 refresh token，另加 Origin 校验防 CSRF。
- **运行期依赖**：复用本机既有 MySQL 8（`127.0.0.1:8806`）与 Redis 7（`127.0.0.1:6606`），不新建容器；本产品专属 schema `wanderchain`，Redis 独立 db index + `wc:` 前缀；凭据只以环境变量名出现，见 D10。
- **建表方式**：不引入 Flyway 或任何迁移框架，用 `schema.sql` + 启动时幂等执行；本阶段库里没有要保住的数据，改结构直接 drop 重建。
- **技术选型**：Spring Data JPA / Spring Data Redis / jjwt 0.12 / `spring-security-crypto` / 不引完整 Spring Security——见 D11。
- **邮箱发码日配额**：每邮箱每自然日 5 封，注册码与重置码合并计数，超限 429 并指明重置时刻——已写入 spec。
- **Q3**：作废——`locked` 状态随锁定机制一并删除，「管理员解锁」不再有意义。
- **Q5**：密码 8–72 字节；邮箱 trim + 转小写后比较——已写入 spec。
- **Q8**：错误码固定集合 6 个——已写入 spec。
- **Q9**：`429` 携带 `Retry-After`——已写入 spec。
- **Q10**：`/me` 固定五个字段——已写入 spec。
- **Q13**：对外标识（`publicId`）永不复用，注销后仍可被引用。
- **Q4**：注销后同一邮箱可重新注册为新账户，旧账户行保持 `deleted`、对外标识不复用。
- **Q16**：全局响应包装只作用于 `/api/auth/**`。
