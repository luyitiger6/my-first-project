# Design

## 决策 1：阈值取「能力 ≤ 2 / 任务 ≤ 30 / 场景 ≤ 60」

依据是 43 个已归档 change 的实测分布：能力数平均 1.2、最大 5；任务数平均 16.5、最大 54；Scenario 平均 15.7、最大 91。

- 能力 ≤ 2 覆盖约 93% 的历史 change，只拦「一个 change 同时改三个以上能力」的混合体
- 任务 ≤ 30 覆盖约 91%，只拦 `rebuild-homepage`（34）、`post-interactions-frontend`（38）、`attractions`（33）、`auth`（54）
- 场景 ≤ 60 覆盖约 95%，只拦 `auth`（88）与 `post-interactions-frontend`（91）

三个阈值都取在历史分布的 90 分位附近而不是中位数：目标不是把 change 切碎，而是拦住「审阅必然失效」的超大变更。

## 决策 2：只校验在飞 change，不追溯归档

历史 change 的规模是既成事实。追溯会迫使改写已归档的规格与任务，制造「为了过闸门而篡改历史」的动机，这与「禁止伪造绿灯」直接冲突。闸门只看 `openspec/changes/` 下非 `archive` 的目录。

## 决策 3：能力数按含 `spec.md` 的目录路径去重计数

OpenSpec 允许嵌套能力路径（如 `identity/user-auth`）。按「`specs/` 下相对路径」计数，而不是数一级目录或数文件：一个能力只有一个 `spec.md`，文件数即能力数，但用路径而非文件名表达，便于超限时直接指出是哪个能力。

## 决策 4：例外走 `scope-exception.md`，且必须到期

硬红灯会制造 gaming：把 31 条任务合并成 30 条、把 3 个能力塞进 2 个目录，规模没有变小，只是看不见了。因此保留一条显式例外通道，但要求 `Reason` / `RegisteredOn` / `Expires` 三字段完整且 `Expires` 未到期。

这与 13 号闸门的 `deferred` 三字段同构：例外是一条会失效的欠账，不是永久豁免。到期后闸门重新判红，逼人要么拆分、要么续期并说明理由。

## 决策 5：阈值写死在脚本顶部，不做配置化

可配置的阈值等于「改个数字就能放行」。把三个数字放在脚本顶部的常量区，修改它需要经过一次真实的代码审阅——这正是我们希望保留的成本。如果今后确有调整必要，应当走一个新的 change，而不是留一个后门。

## 决策 6：与 13 号闸门职责分离

13 号问「每条 Scenario 有没有登记证据」，14 号问「一个 change 一次装多少」。两者都读 `openspec/`，但切入点不同：前者管真相的登记完整性，后者管变更的体量。本变更的能力 `change-scope` 尚未归档，不在 `openspec/specs/` 视野内，13 号不受影响；归档时需同步在 `docs/spec-evidence.json` 登记，否则 13 号会红——这是 13 号棘轮按设计工作的表现。
