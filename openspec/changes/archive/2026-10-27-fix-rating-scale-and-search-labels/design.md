# Design

## Context

动机见 `proposal.md` — Why。下面只记录决定实现方式的事实（均为本轮实测）：

- `frontend/lib/home/mock-data.ts` 第 263–352 行共 9 条景点，`rating` 依次为 `9.6 / 9.3 / 9.5 / 9.2 / 9.0 / 8.8 / 8.7 / 9.9 / 9.9`，全部是 10 分制、一位小数。
- `docs/specs/wanderchain/homepage-u0-contract-mock.md` 第 170 行把 `rating` 的不变量写成「0–5，一位小数」；`homepage-u8-hot-attractions.md` 的 S5 / S12 场景按 `4.25 → 4.3`、`0 / 5 / 4.95` 设计。
- 展示侧只有两处消费：`components/home/hot-attractions.tsx` 的 `Rating {item.rating.toFixed(1)}` 与 `lib/search/query.ts` 的 `Rating ${item.rating.toFixed(1)} · ${count} views`，都只做 `toFixed(1)`，不做任何换算。
- 现有 19 个测试文件、190 条用例中，无一条断言 `rating` 的任何具体取值；`lib/home/data-integrity.test.ts` 只校验双语字段非空白与英文不含中文。
- `lib/search/query.ts` 的 `GROUP_META` 已把三个分组标题与三条回链文案写成英文常量，主规格未把这些字面量钉住。

## Goals / Non-Goals

**Goals:**

- 让 Mock 数据的评分满足文档既定的 0–5 取值域，且不改变任何展示代码。
- 用一条守卫用例把取值域变成可执行的回归约束，而非只写在文档里。
- 把检索分组标题与回链文案的英文字面量钉进主规格，消除「中文类别名 vs 英文标题」的跨能力查阅。

**Non-Goals:**

- 不引入评分校验层（zod / 运行时 schema）——本项目 Mock 数据在编译期由 TypeScript 保证结构，取值域用测试守即可。
- 不改 `toFixed(1)` 的实现，不改排序规则，不改首页/检索的其它任何行为。
- 不追溯更新 `.qoder/english-first-*.png` 六张截图——它们是 `english-first-home` 归档时的历史证据，保留原样。

## Decisions

**1. 统一到 0–5，而不是把文档改成 0–10**

产品面向海外用户，5 分制是英文语境下的默认口径；5 分制下 `Rating 4.6` 无需读者猜分母，10 分制则要。文档已按 0–5 写好两处（不变量表 + 边界场景），改文档等于让唯一写清口径的地方向异常数据让步。

替代方案：保留 10 分制并改文档（被否：`9.9` 落在英文语境里既像 IMDb 又像大众点评，含义不唯一，且要连改 u0 与 u8 两份文档）。

**2. 换算按「保序 + 去重」手工定值，不做机械除以二**

机械 `rating / 2` 会让 `9.3 → 4.65 → 4.7`、`9.5 → 4.75 → 4.8`、`9.6 → 4.8` 三个不同原始值塌成两个值，9.9 还会变成满分 `5.0`。改为按原始先后顺序手工落值，保持「原值越大、新值越大」，原始值相同则新值相同：

| 原值 | 新值 |
|---|---|
| 9.9 | 4.9 |
| 9.9 | 4.9 |
| 9.6 | 4.8 |
| 9.5 | 4.7 |
| 9.3 | 4.6 |
| 9.2 | 4.5 |
| 9.0 | 4.4 |
| 8.8 | 4.3 |
| 8.7 | 4.2 |

替代方案：除以二后四舍五入（被否：破坏排序可辨识度并产生满分）。

**3. 守卫放在 `data-integrity.test.ts` 而不是组件测试**

该文件已是「数据契约守卫」的归口，已按记录维度逐条校验双语字段。评分取值域同属数据契约，放在一起对一个文件即可看完所有数据不变量，也不会因为组件未渲染某个城市而漏掉某条数据。

替代方案：放进 `hot-attractions.test.tsx`（被否：组件测试只覆盖首页上限内的 5 条，剩余 4 条永远测不到）。

**4. 检索分组文案用 ADDED 而非 MODIFIED**

现有「结果展示与空态（英文字段）」已声明「分组名与回链文案 MUST 为英文」，但未钉住字面量。新增一条只做「钉死字符串」的条款，比让 MODIFIED 重抄整条 5 场景的需求块风险更低（重抄时任何一个场景漏掉都会被 strict 校验拦下，但不必要的整块重写本身就是漂移来源）。

## Risks / Trade-offs

- [可见评分值全部变化，用户观感突变] → 这是修正越界数据的必然结果；本轮无真实用户数据，Mock 改动不涉及迁移。
- [换算后出现重复值（两个 4.9）] → 原始数据本就并列，保持并列比人为拉开更诚实。
- [六张已归档截图里仍是 `Rating 8.8`] → 它们是上一轮 change 的验收证据，代表当时状态；本轮不覆写，避免篡改历史证据。
- [守卫只校验 Mock 数据，真实数据源接入后可能再越界] → 条款已写「Mock 数据与将来的真实数据源 MUST 遵守同一约束」；真实数据源接入时应把守卫前移到数据适配层，属后续 change。

## Migration Plan

单次前端提交：改 9 个数值 + 加 1 组守卫用例。无后端改动、无数据库迁移、无依赖升级。回滚即 `git revert` 该子模块提交；回滚后评分回到 10 分制，但主规格的取值域条款仍在，届时校验会立刻暴露不一致——这是期望行为，不是缺陷。
