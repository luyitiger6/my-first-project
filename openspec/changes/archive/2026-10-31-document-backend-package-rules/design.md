# Design

## Context

动机与改动范围见 `proposal.md`。本设计承载待审阅的分包规则正文，尚未替换正式约定。

已核对的现状：
- `docs/conventions/backend-conventions.md` 已有分层图和服务目录职责表，不是空文档；缺少功能子包的使用条件。
- `service/auth/` 的多个接口平铺，共用 `impl/model/support`。`service/post/interaction/` 聚合互动接口、实现、视图和评论游标；`web/post/interaction/` 有对应 HTTP 入口与 DTO。各层不必拥有完全相同的包树。
- `11-conventions-check.ps1` 检查约定索引、固定小节、依赖描述及特定 import 禁止项，不检查业务复杂度、子包深度或是否值得拆分。
- 约定入口当前写“只允许给出指针”“闸门先于文档”，因此新增人工判断规则时，需要同步澄清维护说明，不能假称已有自动守卫。

## Goals / Non-Goals

**Goals:** 用一套判断原则解释简单平铺与复杂聚合，给人和 Agent 提供可直接使用的定位示例；明确规范文字、实例及验证能力的边界。

**Non-Goals:** 不引入新的模块化架构、不强迫所有模块目录完全一致、不规定通用文件数量阈值、不修订 Controller 粒度等无关约定，不扩展为其他项目的分层整改。

## Decisions

### D1. 规则落在现有后端约定，不新增平行规则文档

- 在 `backend-conventions.md` 的“包结构与依赖方向”中整合下方草案，复用并修订已有职责表，避免出现两份不同定义。
- 将现有依赖图的文字解释改为明确的“调用/依赖方向”，例如 `web → service → dao → common`（箭头表示左侧依赖右侧）；不改变既有禁止项或声称闸门覆盖整张图。
- 保留现有“真源声明 / 依赖现状 / 拟引入 / 机械守卫”四节。真源仍引用上游；新规则的日常操作说明只在后端约定维护，规格保存验收要求而不复制示例全文。
- `README.md` 的索引描述增加“分包粒度与类型归属”；其导言与维护说明改为“既有规则引用真源，新约定集中在对应主题文档；可机械校验项由闸门守卫，分包合理性由 change 人工审阅”。不在索引复制下方规则全文，不引用会随归档变动的 change 路径。

不选新建独立分包文档：已有明确入口，新建会增加维护点。不选直接改历史设计：历史工件保留原貌，新规则通过本 change 追溯。

### D2. 待审阅规则正文

以下内容用于整合到后端约定的包结构章节；目录树是代表性节选，不是要求每个模块照抄的模板。

#### 总则：简单平铺，复杂按需聚合

包结构首先服务于阅读和维护。简单功能放在所属模块已有的职责目录中；当功能形成边界清晰的一组文件，继续平铺已经不利于定位时，才按功能聚合为子包。不能仅因为“它是一个子功能”就再复制一套目录。

本项目顶层按技术层组织，层内按业务模块组织：`dao/<域>`、`service/<域>`、`web/<域>`。`auth` 与 `post` 是业务模块；`post/interaction` 是帖子模块内的功能分组，不因此成为独立部署或独立构建的模块。

#### 1. 简单功能默认平铺

- 多个服务接口可以在同一个模块包根并列，分别将实现、模型、辅助类放入已有职责目录；平铺不等于合并成一个大 Service。
- 当前 `auth` 保持这种结构，不为登录、注册、验证码各建一套嵌套目录。
- 没有明确的聚合收益时保持平铺；不为了未来可能增长提前拆包。

```text
service/auth/
├── LoginService.java
├── RegisterService.java
├── impl/
│   ├── LoginServiceImpl.java
│   └── RegisterServiceImpl.java
├── model/
│   ├── LoginAttempt.java
│   └── Registration.java
└── support/
    ├── EmailNormalizer.java
    └── EmailCodeFlow.java
```

#### 2. 复杂功能按需聚合

考虑增加功能子包时，需要同时说明：
- 功能边界是什么，哪些文件主要服务于它；
- 当前平铺会造成什么实际定位或维护困难；
- 聚合如何改善这些困难，跨功能共享类型仍归哪里。

接口、实现、模型、支撑件形成相对完整的一组时，可放在同一功能子包下。当前 `post/interaction` 保留为这种组织方式的例子；不由此自动继续拆出 `comment/impl/model`、`vote/impl/model` 等更深目录。

```text
service/post/
├── PostService.java
├── impl/
│   └── PostServiceImpl.java
├── model/
│   ├── PostCommand.java
│   └── PostView.java
├── support/
│   └── PostReadAccess.java
└── interaction/
    ├── PostInteractionService.java
    ├── impl/
    │   └── PostInteractionServiceImpl.java
    ├── model/
    │   ├── CommentView.java
    │   ├── VoteView.java
    │   └── BookmarkView.java
    └── support/
        └── CommentCursor.java
```

不设置“达到几个文件就必须分包”的阈值；有独立接口、有若干张表、未来可能拆走，都不是单独的充分理由。每增加一层功能目录，都要重新说明实际收益，不能机械递归套用结构。

#### 3. 目录职责统一，目录形状不必一致

| 位置 | 职责 |
|---|---|
| `service/<域>/` 或经审阅的功能包根 | 服务接口 |
| 该服务包的 `impl/` | 接口实现与业务编排 |
| 该服务包的 `model/` | 服务调用的入参、结果与值对象，例如 Command、View、Result、Page |
| 该服务包的 `support/` | 辅助校验、游标、限流等协作件；不是第二个业务编排入口 |
| `dao/<域>/entity/` | 持久化实体；仓储与持久化转换放在同层对应职责目录 |
| `web/<域>/dto/` 或对应功能包的 `dto/` | HTTP 请求与响应契约；Controller 留在所属 web 包 |

- 目录按实际类型创建，不为凑齐 `impl/model/support` 建空壳。
- service 层分子包不意味着 dao、web 各层必须同步复制相同包树；各层按自己的文件归属组织。
- 多个功能共同使用的服务类型优先留在该模块共同的职责目录，不复制多份，也不因同模块共享就搬进全局 `common`。
- `auth` 平铺与 `post/interaction` 聚合可以并存。统一的是职责和分包依据，不是所有模块目录深度完全相同。

#### 4. 类型按所属边界放置

`model` 在这里表示服务层的数据载体，不是所有模型的总目录，也不只允许 Service 实现类引用。Controller 调用服务时可以使用这些类型；HTTP 请求与响应仍使用 web 层 DTO。

例如：持久化对象位于 `dao/post/entity/Post`，服务详情结果位于 `service/post/model/PostView`，HTTP 响应位于 `web/post/dto/PostResponse`。保持既有转换及字段白名单，不将实体直接用作响应，也不将服务入参和结果搬入 Controller 包而造成 service 对 web 的反向依赖。

本项目没有一个同时包含 dao、service、web 的统一 `post/` 根目录，因此不另建跨层的 `post/model` 作为杂物包。其他项目采用模块优先布局或独立契约模块可以有不同放置方式；本规则不把当前目录方案推广为唯一正确架构，也不要求为简单数据机械新增一套 BO。

#### 5. 新增或加深功能子包先说明理由

在相应 change 的设计中，用简短说明和目录示例写清：功能边界、代表性类型、平铺的实际问题、聚合收益、共享类型位置。沿用项目的人工审阅后实施流程；不能把“已写进设计”或“已归档”本身当作用户明确批准的证据。

没有实际收益依据时保持平铺。已有代码不因为新增这条规则就批量搬迁；需要调整时，在涉及该结构的变更中单独说明影响，不在其他功能开发中顺手重排。

#### 6. 机械检查与人工判断分开

现有 `11-conventions-check.ps1` 验证文档自洽性及其列出的分层 import 禁止项，不判断业务复杂度或包层级是否合理。分包粒度、共享归属与聚合收益在 change 人工审阅时判断；不能用闸门通过代替这项判断。

### D3. 文档调整采用轻量验证，不新增工程

- 本提案新增规则要求与场景，保留既有 `dev-conventions` 六项要求；不调整现有自动检查语义。
- 本轮以 `openspec validate document-backend-package-rules --strict` 校验工件，读取工件确认目录示例与当前代码路径一致。
- 实施只改上述两份约定文档后，运行既有 `11-conventions-check.ps1` 检查文档结构与引用兼容性；分包原则按本 change 场景逐项人工核对。
- 不新增依赖，工具复用 OpenSpec CLI 与既有 PowerShell 脚本；不编写或运行业务回归、Maven、前端构建及全量 Harness。完整验收依当前 `AGENTS.md` 后置，另获授权后进行。

不选自动文件数量/深度闸门：其不能可靠表达复杂度判断，且会制造本次不需要的工具维护成本。

## Risks / Trade-offs

- [复杂度存在判断空间] → 默认平铺，新增层级时提供实际依据并人工审阅，不发明未经确认的数字阈值。
- [示例被照抄成固定模板] → 标为节选；明确目录按需创建、各层不必镜像、不得自动递归拆分。
- [约定入口旧表述与人工规则冲突] → 实施时同步澄清导言与维护说明，既有机械约束不弱化，不声称脚本能判断业务合理性。
- [顺手扩大为全仓重构] → 仅改两份约定文档，保留应用、子模块指针及历史归档不动。

## Migration Plan

人工审阅本 change 后，将 D2 整合进后端约定并按 D1 调整索引说明；按 D3 验证。无源码或数据迁移。若撤回约定，只撤回本 change 引入的文档调整，不回退无关改动。正式规格同步、提交和归档另获授权。
