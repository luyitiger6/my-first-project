# Spec Delta

## Purpose

定义 wanderchain 后端认证模块的可观察行为契约：用户账户在同一套状态机下流转、登录响应码随状态唯一确定、任何响应都不携带凭证类字段。

## ADDED Requirements

### Requirement: 用户账户生命周期三态

账户状态 MUST 仅为 `active`、`email_unverified`、`deleted` 三者之一。状态迁移 MUST 只沿下列路径发生，且 `deleted` MUST 是终态。`deleted` 是**账户行**的终态，但 MUST NOT 阻止同一邮箱注册新的账户。注册 MUST 在校验邮箱注册码通过后直接建立 `active` 账户。`email_unverified` 是**保留值**：本变更内不存在任何把账户置入该状态的路径，因此它在生产上不可达，其登录行为只能用测试夹具构造；后续引入产生该状态的入口（如改绑邮箱）的变更 MUST 同时交付退出该状态的路径，否则不得引入。

```text
register(邮箱注册码已校验) -> active
active --本人注销--> deleted

注：本变更不引入任何使账户进入不可登录状态的锁定机制。
登录失败只触发限流，不改变账户状态（见「登录失败以来源限流代替账户锁定」）。
`email_unverified` 在本变更内无入口也无出口，故不出现在迁移图中。
```

#### Scenario: 注册即完成邮箱验证

- **WHEN** 新邮箱提交与缓存一致的注册码完成注册
- **THEN** 账户状态直接为 `active`，并返回访问令牌

#### Scenario: 未验证账户无法登录

- **WHEN** 处于 `email_unverified` 的账户（由测试夹具构造）使用正确凭证尝试登录
- **THEN** 返回 `403` 与 `EMAIL_UNVERIFIED`，不签发令牌，且账户状态保持不变

#### Scenario: 本变更不存在产生未验证状态的入口

- **WHEN** 遍历本变更交付的全部端点，用任意合法输入组合调用
- **THEN** 不存在任何使账户状态变为 `email_unverified` 的路径；该状态只能由测试夹具或直改数据产生

#### Scenario: 本人注销后进入终态

- **WHEN** 已认证用户请求注销自己的账户
- **THEN** 账户状态变为 `deleted`，且该账户的既有令牌立即失效

#### Scenario: 注销后同一邮箱可重新注册

- **WHEN** 使用已注销账户的邮箱重新注册
- **THEN** 返回 `202` 并创建新账户（新的对外标识），旧账户记录保持 `deleted` 不变，其历史内容仍以旧标识引用

#### Scenario: 终态不可被改写

- **WHEN** 对 `deleted` 账户执行登录、注册、验证码校验或重发验证码的任意组合
- **THEN** 账户状态保持 `deleted` 不变，且不会因此返回令牌

#### Scenario: 未定义迁移被拒绝

- **WHEN** 出现上图中未列出的状态迁移（例如 `deleted` 回到 `active`）
- **THEN** 该迁移被拒绝且账户状态保持不变

### Requirement: 登录响应码与账户状态一一对应

登录请求通过凭证校验后，响应状态码 MUST 由账户状态唯一决定：`active` 返回 `200` 并携带访问令牌，`email_unverified` 返回 `403`，`deleted` 返回 `401`。链路上另有两类前置拒绝：来源维度限流触发时 MUST 返回 `429`，与账户状态和凭证是否正确均无关；账户维度要求图形码而调用方未提交或提交错误时 MUST 返回 `400` 与 `CAPTCHA_INVALID`，且该判定先于密码比对。

#### Scenario: 激活账户登录成功

- **WHEN** `active` 账户使用正确凭证登录
- **THEN** 响应状态码为 `200`，响应体包含过期时间与当前用户信息，访问令牌经 `Set-Cookie` 下发而不出现在响应体中

#### Scenario: 未验证账户登录被拒

- **WHEN** `email_unverified` 账户使用正确凭证登录
- **THEN** 响应状态码为 `403`，且不携带访问令牌

#### Scenario: 已注销账户登录被拒

- **WHEN** `deleted` 账户使用正确凭证登录
- **THEN** 响应状态码为 `401`，且不携带访问令牌

#### Scenario: 不返回映射之外的状态码

- **WHEN** 登录请求的凭证格式合法
- **THEN** 其响应状态码只可能是 `200`、`400`、`401`、`403`、`429` 之一；`400` 仅出现在图形码校验失败或入参校验失败的情形，且不出现任何表示账户被锁定的状态码

### Requirement: 凭证校验先于状态判定

登录 MUST 先校验邮箱是否存在与密码是否匹配；只要凭证校验不通过，MUST 一律返回 `401`，与目标账户处于何种状态无关。`403` MUST 仅在凭证正确时才可能出现。来源维度限流 MUST 先于凭证校验执行，否则限流对爆破无效。

#### Scenario: 邮箱不存在

- **WHEN** 使用未注册的邮箱登录
- **THEN** 返回 `401`，且响应体与「密码错误」完全一致

#### Scenario: 未验证账户密码错误

- **WHEN** `email_unverified` 账户使用错误密码登录
- **THEN** 返回 `401` 而不是 `403`

#### Scenario: 已注销与凭证错误不可区分

- **WHEN** 分别对 `deleted` 账户与「密码错误」场景发起登录
- **THEN** 两次响应的状态码、错误码与提示文案完全相同

### Requirement: 登录失败以来源限流代替账户锁定

登录失败 MUST NOT 使账户进入不可登录状态，也 MUST NOT 改变账户状态。失败只驱动两类限流：

- **账户维度**：同一账户连续失败达到阈值（默认 5 次）后，后续登录 MUST 要求提交图形验证码；一次成功登录 MUST 将连续失败计数清零。
- **来源维度**：同一来源在限流窗口内的失败达到上限时，MUST 返回 `429` 并携带 `Retry-After`。来源 MUST 是**客户端 IP**，按下列规则取得：仅当请求来自已登记的代理层时才采信其转发头中的地址；无法确认真实来源时 MUST 按「未知来源」单独计数，MUST NOT 与已解析来源合并，也 MUST NOT 因此跳过限流。IPv6 地址 MUST 按其 `/64` 前缀聚合。来源维度计数 MUST 累计该来源的全部失败且不区分账户，使「单来源撞多个账户」落入同一额度。

#### Scenario: 连续失败后要求图形码

- **WHEN** 同一账户连续失败达到阈值后再次发起登录
- **THEN** 未提交有效图形码时返回 `400` 与 `CAPTCHA_INVALID`，不进行密码比对

#### Scenario: 成功登录后放宽要求

- **WHEN** 账户在触发图形码要求后完成一次成功登录
- **THEN** 连续失败计数清零，再次登录不再要求图形码

#### Scenario: 来源超阈返回 429

- **WHEN** 同一来源在限流窗口内失败次数达到上限
- **THEN** 返回 `429` 并携带 `Retry-After`，且不进行密码比对

#### Scenario: 无法确认真实来源时单独计数

- **WHEN** 请求未经已登记的代理层，或转发头缺失、格式非法
- **THEN** 该请求按「未知来源」单独计数，不与任何已解析来源共享额度，也不被直接放行

#### Scenario: 伪造转发头不扩容额度

- **WHEN** 调用方在直达请求中自行携带转发头、声称来自另一个 IP
- **THEN** 该请求仍按「未知来源」计数，声称的地址不被采信

#### Scenario: IPv6 同前缀共享额度

- **WHEN** 同一 `/64` 前缀下的多个 IPv6 地址连续失败
- **THEN** 它们共用同一来源计数，不因地址变化而重新获得额度

#### Scenario: 单来源撞多账户共用额度

- **WHEN** 同一来源对多个不同账户连续失败
- **THEN** 全部失败计入同一来源计数，达到上限后该来源返回 `429`

#### Scenario: 限流不改变账户状态

- **WHEN** 同一账户连续失败任意次数（含远超阈值）
- **THEN** 账户状态保持原值不变，且仍能以正确凭证登录成功（可能需先通过图形码）

### Requirement: 用户信息接口的响应不得包含凭证类字段

`GET /api/auth/me` 的响应体 MUST NOT 出现 `password_hash`、`salt`、`verification_code` 这三个键（任意嵌套层级同样适用），且 MUST NOT 包含该账户已存储的密码哈希值。所有响应 MUST 经统一响应包装出站，不得由各端点自行拼装响应体。本 Requirement 的覆盖范围限于用户信息接口的响应，其余端点与其余敏感字段的防护范围另行确定。该响应的字段集合 MUST 恰为 `publicId`、`email`、`displayName`、`status`、`createdAt` 五项。

#### Scenario: 用户信息响应只含白名单字段

- **WHEN** 持有有效令牌请求当前用户信息
- **THEN** 响应体的字段集合是已登记白名单的子集，且不含凭证类字段

#### Scenario: 不复述已存哈希

- **WHEN** 请求当前用户信息
- **THEN** 响应文本中检索不到该账户存储的密码哈希值

#### Scenario: 未登记字段即失败

- **WHEN** 用户信息响应中出现了白名单未登记的字段
- **THEN** 契约校验失败，视为违反本 Requirement

#### Scenario: 绕过统一包装即失败

- **WHEN** 任一端点试图不经过统一响应包装直接写出响应体
- **THEN** 该实现被视为违反本 Requirement

### Requirement: 敏感凭证以单向哈希持久化

密码与邮箱验证码 MUST 以单向哈希形态持久化。盐 MUST 内嵌于哈希值本身，MUST NOT 单独存储为独立字段，也 MUST NOT 经由任何响应返回。

#### Scenario: 密码不可还原

- **WHEN** 直接读取持久化层中的账户记录
- **THEN** 只能读到密码哈希，读不到任何形式的明文密码

#### Scenario: 验证码只存哈希与存活时间

- **WHEN** 系统生成图形验证码与邮箱注册码
- **THEN** 共享缓存只保存两者的摘要与剩余存活时间，明文仅存在于生成时刻的内存与投递通道中

#### Scenario: 验证码不可跨账户复用

- **WHEN** 使用账户 A 的验证码去校验账户 B
- **THEN** 校验失败，且不影响账户 B 的状态与失败计数

### Requirement: 令牌签发与即时失效

登录成功签发的访问令牌 MUST 带有效期且不可被客户端伪造。账户离开 `active` 状态、被注销、主动登出或重置密码后，其既有令牌 MUST 立即失效，不得等待自然过期。

令牌 MUST 通过响应头 `Set-Cookie` 下发，cookie MUST 携带 `HttpOnly` 与 `SameSite=Lax`，生产环境 MUST 携带 `Secure` 且 MUST NOT 允许 `Domain` 跨越到子域。登录与注册响应体 MUST NOT 包含令牌明文，客户端 JavaScript MUST NOT 能读到令牌。受保护请求 MUST 从该 cookie 读取令牌，不依赖 `Authorization` 头。登出与注销的响应 MUST 清除该 cookie。

#### Scenario: 令牌带有效期

- **WHEN** 登录成功
- **THEN** 响应体中的过期时间、`Set-Cookie` 的 `Max-Age` 与令牌内部声明的生命周期三者一致

#### Scenario: 令牌不出现在响应体

- **WHEN** 登录或注册成功
- **THEN** 响应体中检索不到令牌字符串，令牌只出现在 `Set-Cookie` 头中

#### Scenario: 认证 cookie 属性齐备

- **WHEN** 检查登录成功返回的 `Set-Cookie`
- **THEN** 该 cookie 带 `HttpOnly`、`SameSite=Lax` 与 `Path=/`，且在生产 profile 下带 `Secure`

#### Scenario: 登出清除认证 cookie

- **WHEN** 用户调用登出端点
- **THEN** 响应中的 `Set-Cookie` 将该 cookie 置空并将 `Max-Age` 置为 `0`

#### Scenario: 注销后旧令牌失效

- **WHEN** 用户注销账户
- **THEN** 该账户此前签发的全部令牌在下一次请求时即被拒绝

#### Scenario: 登出后令牌失效

- **WHEN** 用户主动登出
- **THEN** 用于本次登出的令牌不能再用于访问受保护资源

#### Scenario: 非激活账户持有效令牌

- **WHEN** 持有未过期令牌的账户状态不是 `active`
- **THEN** 访问受保护资源返回 `401`，不返回 `403`

#### Scenario: 重置密码后旧令牌失效

- **WHEN** 账户通过邮箱重置码成功设置新密码
- **THEN** 该账户此前签发的全部令牌在下一次请求时即被拒绝，需用新密码重新登录

### Requirement: 写请求的来源校验

由于令牌存放在 cookie 中，浏览器会自动附带它，因此所有可能产生状态变更的请求 MUST 在业务处理前完成来源校验：`Origin`（缺失时回退 `Referer`）的源 MUST 属于已登记站点来源；不匹配或两者皆缺失时 MUST 返回 `403` 与 `CROSS_SITE_REJECTED`，MUST NOT 执行任何写操作。`GET` 类请求不做该校验，但 MUST NOT 产生任何状态变更。该校验 MUST 独立于登录判定：未通过来源校验的请求不再进行凭证与账户状态判定。

#### Scenario: 跨站写请求被拒

- **WHEN** 携带有效认证 cookie 的 `POST`、`PUT`、`PATCH` 或 `DELETE` 请求的 `Origin` 不属于已登记站点来源
- **THEN** 返回 `403` 与 `CROSS_SITE_REJECTED`，且不执行任何写操作

#### Scenario: 同源写请求通过

- **WHEN** 同样的请求来自已登记的站点来源
- **THEN** 正常执行，不受来源校验干扰

#### Scenario: 来源头缺失时回退 Referer

- **WHEN** 写请求没有 `Origin` 但有 `Referer`
- **THEN** 以 `Referer` 的源参与校验；两者皆缺失时拒绝

#### Scenario: 校验先于凭证与状态判定

- **WHEN** 一个跨站写请求同时携带了无效凭证
- **THEN** 返回 `CROSS_SITE_REJECTED` 而不是 `UNAUTHENTICATED`，不进行凭证比对

### Requirement: 注册验证码链路

注册 MUST 分两步：先凭图形验证码换发邮箱注册码，再凭邮箱注册码完成注册。两类码均 MUST 一次性；邮箱注册码 MUST 存于共享缓存且存活时间 MUST NOT 超过 300 秒（默认 300 秒）；比对成功后 MUST 在创建账户的同一处理中删除该键，不得等到自然过期。

#### Scenario: 图形码校验通过才发码

- **WHEN** 提交的图形验证码答案正确
- **THEN** 返回 `202` 并向该邮箱投递注册码，该图形码随即作废

#### Scenario: 图形码可随时重新获取

- **WHEN** 调用方再次请求图形验证码
- **THEN** 返回新的 `captchaId` 与对应图形，各张图形码在各自存活时间内独立可校验（不要求旧 `captchaId` 随之失效）；重复调用不影响已发出的邮箱注册码

#### Scenario: 图形码错误不发码

- **WHEN** 提交错误的图形验证码答案
- **THEN** 返回 `400` 与 `CAPTCHA_INVALID`，不投递邮件、不生成邮箱注册码

#### Scenario: 注册码超过存活时间后失效

- **WHEN** 在注册码写入缓存超过存活时间（默认 300 秒）后提交注册
- **THEN** 返回 `400` 与 `INVALID_CODE`，不创建账户

#### Scenario: 注册码一次性

- **WHEN** 用同一注册码完成注册后再次提交
- **THEN** 第二次返回 `400` 与 `INVALID_CODE`，不创建第二个账户

#### Scenario: 验证成功后立即删除缓存键

- **WHEN** 注册码比对成功并创建账户
- **THEN** 该注册码的缓存键在同一次处理内被删除，无需等到存活时间到期；此后即使缓存中残留其他键也拒绝该码

#### Scenario: 重新发码使旧码失效

- **WHEN** 用户在冷却结束后重新请求注册码
- **THEN** 缓存中旧注册码立即失效，只有最新的可用

#### Scenario: 重发频率受限

- **WHEN** 在重发冷却窗口内再次请求注册码
- **THEN** 返回 `429` 并携带 `Retry-After`，不生成新注册码、不触发投递

#### Scenario: 比对失败次数超限

- **WHEN** 同一注册码的比对失败次数达到配置上限
- **THEN** 该注册码作废，必须重新走图形码换发流程

### Requirement: 注册不得泄露邮箱是否已存在

注册链路的两个步骤 MUST NOT 让调用方区分「邮箱已注册」与「邮箱未注册」：请求注册码时，对已存在邮箱 MUST 返回与正常一致的响应但 MUST NOT 投递；提交注册时，对已存在邮箱 MUST 返回与「注册码错误」相同的状态码、错误码与提示。

#### Scenario: 已注册邮箱请求注册码

- **WHEN** 使用未注销的已注册邮箱请求注册码
- **THEN** 返回 `202` 且响应体与正常情形一致，但不投递邮件

#### Scenario: 已注册邮箱提交注册

- **WHEN** 使用未注销的已注册邮箱提交一份格式合法的注册请求
- **THEN** 响应与「注册码错误」逐字段相等，且不产生第二份账户

#### Scenario: 已注销邮箱可重新注册

- **WHEN** 使用已注销账户的邮箱请求注册码并完成注册
- **THEN** 正常投递并创建新账户，旧账户记录保持不变

### Requirement: 注册入参与邮箱规范化

注册与登录的入参 MUST 先规范化再参与判定：邮箱 MUST 去除首尾空白并转为小写后比较，密码长度 MUST 在 8 到 72 字节之间。不满足约束的请求 MUST 返回 `400` 与错误码 `VALIDATION_FAILED`，不得创建账户。

#### Scenario: 邮箱大小写与空白不影响唯一性

- **WHEN** 先以带首尾空白与大写形式的邮箱注册，再以全小写同一邮箱注册
- **THEN** 第二次请求按「重复注册」处理，不产生第二个账户

#### Scenario: 密码长度越界被拒

- **WHEN** 使用 7 字节或 73 字节的密码注册
- **THEN** 返回 `400` 与 `VALIDATION_FAILED`，不创建账户

### Requirement: 密码找回

密码找回 MUST 复用注册的两层码链路：先凭图形验证码换发邮箱重置码，再凭邮箱重置码设置新密码。重置码 MUST 存于共享缓存，存活时间与注册码一致（默认 300 秒），一次性，验证成功即删。重置成功 MUST 更新密码哈希、使该账户既有令牌全部失效，且 MUST NOT 改变账户状态。对未注册或已注销的邮箱，请求重置码 MUST 返回与正常一致的响应但 MUST NOT 投递。

#### Scenario: 重置码可换新密码

- **WHEN** 提交与缓存一致的重置码与合法新密码
- **THEN** 密码哈希更新为新密码的哈希，返回 `200`，且新密码可立即登录

#### Scenario: 重置不改变账户状态

- **WHEN** 对 `active` 账户完成密码重置
- **THEN** 账户状态仍为 `active`，重置请求次数不产生任何锁定效果

#### Scenario: 重置码一次性且成功即删

- **WHEN** 用同一重置码第二次提交
- **THEN** 返回 `400` 与 `INVALID_CODE`，密码保持不变

#### Scenario: 未注册邮箱请求重置码

- **WHEN** 使用未注册或已注销的邮箱请求重置码
- **THEN** 返回 `202` 且响应体与正常情形一致，但不投递邮件

#### Scenario: 重置码错误不暴露账户存在性

- **WHEN** 对未注册邮箱提交一份格式合法的重置请求
- **THEN** 响应与「重置码错误」逐字段相等

#### Scenario: 重置码比对失败次数超限

- **WHEN** 同一重置码的比对失败次数达到配置上限
- **THEN** 该重置码作废，须重新走图形码换发流程

### Requirement: 邮箱发码日配额

注册码与重置码的投递 MUST 同时受两道独立限制：同一邮箱的重发冷却（默认 60 秒）与日配额（默认 5 封/自然日，两类码合并计数）。日配额 MUST 在投递决策之前比对；图形码错误或冷却命中的请求 MUST NOT 消耗配额；通过这两道校验的请求 MUST 计入配额，即使该邮箱最终不会被投递。超限时 MUST NOT 生成新码、MUST NOT 投递，并返回 `429` 与指向配额重置时刻的 `Retry-After`；该响应 MUST NOT 因邮箱是否已注册而不同。配额计数键 MUST 由邮箱摘要构成，MUST NOT 含邮箱明文。额度与冷却参数均 MUST 外部配置。

#### Scenario: 日配额用尽后不再投递

- **WHEN** 同一邮箱在自然日内已达配额上限后再次请求注册码或重置码
- **THEN** 返回 `429` 与 `RATE_LIMITED`，`Retry-After` 指向次日零点的剩余秒数，且不生成新码、不投递

#### Scenario: 配额在自然日边界重置

- **WHEN** 跨过自然日零点后该邮箱再次请求
- **THEN** 配额恢复为完整额度

#### Scenario: 冷却命中或图形码错误不消耗配额

- **WHEN** 在冷却窗口内重发，或提交了错误的图形码答案
- **THEN** 该次请求返回各自对应的错误码，且不增加日配额计数

#### Scenario: 配额响应不区分邮箱是否已注册

- **WHEN** 分别用已注册与未注册邮箱把配额用尽后再请求
- **THEN** 两次响应的状态码、错误码与 `Retry-After` 含义相同，不可据此判断注册状态

#### Scenario: 配额键不含邮箱明文

- **WHEN** 直接检查缓存中的配额键
- **THEN** 键名中检索不到邮箱原文，只含其摘要与日期

### Requirement: 统一错误结构

认证端点返回错误时 MUST 使用统一错误结构，含稳定的错误码与人类可读提示；`429` 响应 MUST 额外携带 `Retry-After`。错误码 MUST 取自固定集合：`UNAUTHENTICATED`（`401`）、`EMAIL_UNVERIFIED`（`403`）、`CROSS_SITE_REJECTED`（`403`）、`INVALID_CODE`（`400`）、`CAPTCHA_INVALID`（`400`）、`RATE_LIMITED`（`429`）、`VALIDATION_FAILED`（`400`）。其中 `403` 对应两个错误码，客户端 MUST 以错误码而非状态码区分两者。新增错误码属于契约变更。

#### Scenario: 错误响应结构一致

- **WHEN** 任一认证端点返回 `4xx` 或 `5xx`
- **THEN** 响应体包含错误码与提示两个字段，且不含任何用户凭证或内部标识

#### Scenario: 限流响应可被客户端解读

- **WHEN** 返回 `429`
- **THEN** 响应体包含错误码 `RATE_LIMITED`，响应头包含 `Retry-After`，客户端无需额外请求即可展示剩余等待时间

#### Scenario: 错误码取自固定集合

- **WHEN** 任一认证端点返回错误
- **THEN** 其错误码属于固定集合，且与状态码的对应关系与上述一致
