# Design

## Context

动机见 `proposal.md` 的 Why 段落，此处只记录影响实现方式的现状与约束。

- 闸门体系是「文件名排序 + 独立进程 + 只认退出码」：`harness/run-all.ps1` 遍历 `harness/checks/*.ps1`，`NN-` 前缀决定执行顺序，脚本之间不共享状态。新增闸门不需要改总控脚本，代价是新闸门无法从总控拿到任何上下文，只能自己读文件。
- 文档侧唯一入口是 `AGENTS.md`，它同时是给人看的说明书和给 agent 的地图。`README.md` 是面向人的副本，两者内容有重叠但不保证同步。
- `AGENTS.md` §6 的闸门清单是一张 Markdown 表格，行文随解释变化，没有固定列结构；直接对表格做正则解析，一旦有人加一行说明文字就会误判。
- 编写环境是 Windows PowerShell 5.1：`.ps1` 文件若不带 UTF-8 BOM，中文注释会按 ANSI 解码，导致引号边界错乱并抛出 ParserError。仓库既有闸门全部是 UTF-8 with BOM。

## Goals / Non-Goals

**Goals:**

- 让「文档写的闸门集合」与「磁盘上真实存在的闸门」的偏差自动变成退出码 1，不依赖人偶然翻到。
- 让「已下线技术栈的文件名」出现在文档里时自动变成退出码 1，覆盖比闸门清单更容易漏的一类漂移。
- 新闸门自身遵守既有约定：`NN-` 前缀、`exit 0/1`、不交互、只读文件系统。
- 文档中不再写死可增长的数量，从源头减少下一次必须改文档的理由。

**Non-Goals:**

- 不校验 `README.md` 与 `AGENTS.md` 的语义一致性。两者叙述口径不同，机器无法判断「说清楚」与「说得更细」的差别。
- 不做目录树与实际文件系统的逐条比对。目录树是刻意省略过的（只列关键文件），逐条比对会把「有意省略」误判为漂移。
- 不校验「人是否审阅过 proposal」。见 Decisions 第 4 条。

## Decisions

### 1. 用内嵌标记而不是解析表格来获取闸门清单

在 `AGENTS.md` §6 的 harness 章节放一行 HTML 注释：

```
<!-- harness-checks: 00-submodule-check 01-compile ... 07-doc-consistency -->
```

闸门读取该标记，与实际 `harness/checks/*.ps1` 的 BaseName 集合做**双向**比对：实际有而标记没有 → 报「缺少实际存在的闸门」；标记有而实际没有 → 报「写了不存在的闸门」。

- 为什么不是解析表格：表格是给人读的，随时会加说明列或调整行文，正则一碰就碎；HTML 注释对人不可见，对机器是稳定的单一契约。
- 为什么是双向：单向只能抓住「加了闸门忘了写文档」，抓不住「删了闸门文档还在吹」，后者危害更大——文档承诺了不存在的护栏。
- 替代方案：把闸门清单外置成 `harness/checks.json`，由文档与脚本共同读取。否决理由：多一个需要人记得同步的文件，等于把漂移点从两处变成三处。

### 2. 已下线技术栈用 token 黑名单，且只扫两个入口文档

当前黑名单为 `App.vue`、`App.spec.ts`、`src/main.ts`、`TodoApp`、`Todo 界面`，用 `Select-String -SimpleMatch` 扫 `AGENTS.md` 与 `README.md`。

- 选 `-SimpleMatch` 而非正则：这些 token 里有点号、斜杠和中文，正则反而要处处转义，且没有模式匹配需求。
- 只扫两个入口文档：`openspec/changes/archive/` 下的历史工件**必须**保留旧技术栈描述，那是审计记录，扫了就等于要求篡改历史。
- 淘汰方式是把 token 加进数组，而不是删除判断逻辑——黑名单只增不减，才留得住「这个栈已经下线」这件事。

### 3. 闸门失败即 `exit 1`，不做 warning 模式

护栏的价值在于拦截，warning 在 CI 与 agent 环境里等价于放行。因此文档不一致与真实编译失败享受同级待遇：都让 `run-all.ps1` 返回 1。

- 代价：改文档风格时可能被自己拦住。缓解手段是让报错信息直接给出「标记里写了什么、磁盘上有什么」，修一次只需改一行注释。

### 4. 明确不把「人工审阅」做成闸门

`AGENTS.md` 规定 proposal 必须先经人审阅放行才能实施，这是全流程唯一的强制人工卡点。本次刻意**不为它加闸门**：

- 机器无法验证「人是否真的读过并认可」。任何自动检查（例如查审批字段、查 commit message 里的 approval 字样）都只能验证**留痕**，而留痕可以绕过——那会产出一道永远绿的假闸门，比没有闸门更危险。
- 因此人工卡点继续以流程约定的形式存在，并明确记为已知边界（见 Risks）。真正的改进方向是让 agent 在 proposal 写完后停下来等指令，而不是再加一道机器检查。

### 5. 文档里删除写死的数量，而不是维护它

`README.md` 中「七道闸门（00–06）」「00–06 全部执行」改为「闸门链」「跑完整条闸门链」。闸门数量是**会增长的量**，写进文档意味着每加一道都要回来改一次，而漏改只会误导人。

- 唯一的例外是 `AGENTS.md` §6 的清单本身：它必须逐条列出（人需要看顺序），但已由第 1 条决策的标记机制兜住。

### 6. 删除前用 `git ls-files` 确认未跟踪

`frontend/dist/`、`frontend/src/` 与 `.scaffold-tmp/` 在删除前先执行 `git ls-files -- <路径>` 并要求计数为 0。理由：`frontend/` 是 submodule，路径判断容易出错，用版本库自己回答「这个文件是否属于任何一份提交」比人工推理可靠。

## Risks / Trade-offs

- **标记与实际不一致时，闸门自己也会被骗** → 标记是手工维护的，理论上可以被人为改成与实际一致而掩盖真实问题。缓解：标记只声明文件名集合，不声明行为；闸门只能保证「名字对得上」，不能保证「闸门本身有效」。这属于可接受的边界，并被写进 Risky 的下一层——闸门是否有效仍需人看代码。
- **黑名单会过期** → 黑名单只增不减，长期会积累不再相关但也不会误伤的词。缓解：误伤成本低（改文档措辞即可），漏检成本高（agent 按错的地图动手），因此偏向宁多不漏。
- **人工审阅仍然没有机器兜底** → 见 Decisions 第 4 条。当前只能靠流程纪律；若后续需要，应做的是让 agent 在关键节点主动停下，而不是伪造一道审批闸门。
- **BOM 约束是隐性陷阱** → 任何新建 `.ps1` 若忘记 UTF-8 BOM，会在 PowerShell 5.1 下抛 ParserError，且报错位置在中文字符串中间，极易误判为语法问题。缓解：新建脚本后立即单跑一次，看到 ParserError 先查 BOM 再查语法。

## Migration Plan

1. 先改文档（`AGENTS.md`、`README.md`、`03-static-guard.ps1` 头注释），让真相先落地。
2. 再建 `07-doc-consistency.ps1`，此时标记与磁盘已经一致，新闸门首跑应为绿；随后故意改错标记做一次负向验证，确认能返回 1，再还原。
3. 清理未跟踪残留物，最后跑一次完整 `run-all.ps1`，八道闸门全绿才算完成。
4. 回滚方式：本次无运行时改动，回滚只需 `git checkout` 文档与脚本、删除新增闸门文件；已删除的残留物均未跟踪，无需恢复其内容（需要时可从 `frontend` 子模块的提交历史重建构建产物）。
