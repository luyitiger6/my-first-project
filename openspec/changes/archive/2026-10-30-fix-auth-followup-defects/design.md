# Design

## Context

现状与约束（动因见 proposal.md - Why）：

- 图形码由 `GET /api/auth/captcha` 无状态发放，每次返回新 `captchaId`，各张在存活期内独立可校验。前端 `loadCaptcha()` 每次成功都会 `setCaptchaAnswer('')`，失败则 `setError(...)`。
- 登录链路默认不取码，只有 `CAPTCHA_INVALID` 才取；注册第一步进页面就取一张，因为提交必须带答案。
- `isCaptchaRequired(cause)` 精确判定 `AuthApiError.code === 'CAPTCHA_INVALID'`，是唯一可靠的「码被拒」信号；`429`、网络错误、字段校验 `400` 都不会命中。
- `logout()` 目前被 `account-menu.tsx` 以 `onClick={() => void logout()}` 调用，生产代码中仅此一处，且没有任何 `.catch`。
- `wanderchain-auth-frontend` 主 spec 的「注册走两步验证码链路」正文写「8 到 72 字节」，同块 Scenario 却写「8 个字符」，两者互斥。

## Goals / Non-Goals

**Goals:**

- 让「换不换码」由一个可判定的信号决定，而不是由一个界面状态（`step`）决定。
- 让错误提示始终描述用户真正撞上的那次失败。
- 让登出失败在行为上等价于登出成功（界面层面），只是在副作用上不再泄漏异常。
- 消除主 spec 内字节/字符互斥，使实现者不需要在两条互斥条款之间自行裁决。

**Non-Goals:**

- 不改后端：不新增错误码、不改 `CAPTCHA_INVALID` 语义、不改图形码 TTL 与一次性规则。
- 不改密码校验口径（仍是 8–72 字节），只改提示的计量单位表述。
- 不引入全局错误提示体系或 toast 组件——本次仍在表单内联提示范围内解决。
- 不为登出增加乐观锁、重试或队列；一次请求、一次收敛。

## Decisions

### D1. 换码条件收窄为 `isCaptchaRequired(cause)` 单条件

把 catch 里的 `if (isCaptchaRequired(cause) || (isRegister && step === 'captcha'))` 改为只判 `isCaptchaRequired(cause)`。

- 理由：`step === 'captcha'` 描述的是「用户现在在第几步」，不是「这张码是否已被消费」。`429` 在限流层就被拒，根本没走到图形码校验，此时换码纯属误伤；网络错误更不可能消费码。
- 已考虑并否决：保留无条件刷新、只优化文案（被否：用户仍需重看新图、重输答案，成本没降）；由前端记住「上次提交是否带过码」来判断（被否：多一份状态，且和后端一次性语义仍然对不上）。

### D2. 刷新失败走独立提示通道，与原始错误并存

`loadCaptcha` 失败时只写一条独立提示位 `captchaNotice`（文案「图形码刷新失败，请手动刷新」），**不写 `error`，也不清空 `captcha`/`captchaAnswer`**；成功时清除该提示。自动换码与手动点 Refresh 两条路径共用这条提示，`error` 只描述用户真正撞上的那次提交失败。

- 理由：错误位是单一字段，后写覆盖先写。换码是失败处理的附带动作，它自己失败时既不能抢走主因，也不能静默——用户手里的码可能已经作废，不提示就只能靠猜（用户裁决：两条路径都必须提示）。
- 已考虑并否决：让 `loadCaptcha` 继续写 `error`（被否：会覆盖主因，用户会以为密码错了）；在 catch 里先存下原消息、刷新后再写回（被否：次序脆弱，后续任何人插入一次 `setError` 就会复发）；只在自动换码失败时提示、手动路径沉默（被否：手动刷新失败是用户主动发起的动作，没有其它反馈通道）。

### D3. 密码提示改为字节口径

`PASSWORD_HINT` 改为 `8-72 bytes (about 3-24 Chinese characters)`。

- 理由：常量本身就是 `PASSWORD_MIN_BYTES` / `PASSWORD_MAX_BYTES`，提示与约束同单位才不会误导；中文与 emoji 用户尤其容易按「8 个字符」估算。换算示例由同一组常量除以 UTF-8 汉字字节宽（3）算出：下限取 `ceil(8/3)=3`（2 个汉字只有 6 字节，达不到下限），上限取 `floor(72/3)=24`，不硬编码魔法数。
- 已考虑并否决：只写字节不附换算（被否：用户裁决要提示换算，纯字节表述对中文用户不直观）；把前端改为按字符计数并与后端对齐（被否：那要改后端校验契约，超出本次范围）。

### D4. 登出失败在 provider 内收敛

`logout` 改为 `try { await logoutRequest() } catch { /* 故意忽略 */ } finally { setUser(null); setStatus('guest') }`，对外不再以 rejection 结束。

- 理由：调用点只有一处，且是 `void logout()`，没有消费 rejection 的通道；规格要求登出失败仍回到访客态，收敛点放在 provider 内才能保证所有未来调用方都不必各自处理。
- 已考虑并否决：由每个调用方 `.catch(() => {})`（被否：契约靠调用方自觉，新增一处调用就会复发）；请求层 `logoutRequest` 内部吞异常（被否：请求层应如实反映失败，吞异常会掩盖真实网络问题）。

### D5. delta 用 REMOVED + ADDED 而不是 MODIFIED

「注册走两步验证码链路」整块改由新命名的「注册按两步验证码链路并遵守字节口径」承接，Requirement 总数不变。

- 理由：本次需要改写既有 Scenario 的措辞（「8 个字符」→「按字节表述」）。按本项目约束，MODIFIED 必须逐字复制既有 Scenario，就地改措辞会让归档合并时丢细节；REMOVED + ADDED 是唯一能既改措辞又保留审计链的写法。
- 已考虑并否决：保留旧 Scenario 再加一条「必须按字节」的新 Scenario（被否：主 spec 内会同时存在两条互斥条款，把矛盾固化进真相层）；直接编辑主 spec（被否：绕过 delta 这一唯一变更通道）。

### D6. 测试补齐方式

在既有 `auth-form.test.tsx`、`auth-provider.test.tsx` 内追加用例，不新建测试文件。

- 理由：改动全在这两个模块内，既有测试夹具（fetch mock、AuthProvider 包装）可直接复用；新建文件会重复搭脚手架。
- 已考虑并否决：为「换码时机」单独建集成级测试（被否：本次没有跨模块协作，单元级已能覆盖全部四条新 Scenario）。

## Risks / Trade-offs

- [收窄换码后，若后端将来在图形码缺失时返回别的错误码] → 已由 `isCaptchaRequired` 单一判据兜住：只要不是 `CAPTCHA_INVALID` 就不换码，届时新增错误码必须显式纳入判据，行为变化会被测试发现而非静默漂移。
- [自动换码失败时保留已被消费的旧码] → 用户拿旧码重试必然再失败；代价是一次无效提交，收益是不会丢失已输入答案、错误提示正确。用户可手动点 Refresh 换新码。
- [登出静默吞异常可能掩盖后端长期 5xx] → 界面行为与后端健康解耦是刻意的；可观测性依赖服务端日志，不在前端补。若日后需要前端口径，应新增独立的告警通道而不是恢复抛错。
- [Requirement 换名会打断「标题即稳定标识」的惯例] → 本次仅此一条，且新旧标题都不被其它 spec 或代码引用（已检索确认），代价可控。
