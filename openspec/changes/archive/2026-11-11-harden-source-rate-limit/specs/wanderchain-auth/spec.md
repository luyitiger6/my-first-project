## ADDED Requirements

### Requirement: 全站写操作来源限流

除 `/api/auth/**` 之外，所有 `/api/**` 的写请求（方法不属于 `GET`、`HEAD`、`OPTIONS`）MUST 按来源限流：同一来源在一分钟窗口内共享一个额度（默认 60 次），超限 MUST 返回 `429`、错误码 `RATE_LIMITED` 与 `Retry-After`。来源识别 MUST 复用「登录失败以来源限流代替账户锁定」的规则；无法确认真实来源时 MUST 使用独立的「未知来源」桶（默认 20 次/分钟），MUST NOT 与已解析来源合并，也 MUST NOT 跳过限流。计数 MUST 存放在多实例共享的缓存中，使额度对全部实例生效；缓存不可用时 MUST 放行写请求并记录告警。

#### Scenario: 来源超限返回 429

- **WHEN** 同一来源在一分钟窗口内的写请求达到额度上限后再次发起写请求
- **THEN** 该请求返回 `429`、错误码 `RATE_LIMITED` 与 `Retry-After`，且不执行写操作

#### Scenario: 读请求不占写额度

- **WHEN** 同一来源在写额度耗尽后发起 `GET`、`HEAD` 或 `OPTIONS` 请求
- **THEN** 请求正常处理，不返回 `429`

#### Scenario: 认证端点不重复计数

- **WHEN** 同一来源调用 `/api/auth/**` 下的接口
- **THEN** 不消耗本 Requirement 的写额度，该前缀的行为由认证自身的限流规则覆盖

#### Scenario: 未知来源独立额度

- **WHEN** 无法确认真实来源的写请求在一分钟内达到独立额度上限
- **THEN** 这些请求返回 `429`，且已解析来源的写请求不受影响

#### Scenario: 多实例共用同一额度

- **WHEN** 同一来源的写请求分布到两个后端实例
- **THEN** 两个实例读取同一计数，合计超限后返回 `429`

#### Scenario: 缓存不可用时放行

- **WHEN** 共享缓存不可达，无法读写写操作计数
- **THEN** 写请求被放行并记录告警，MUST NOT 返回 `429`

## MODIFIED Requirements

### Requirement: 登录失败以来源限流代替账户锁定

登录失败 MUST NOT 使账户进入不可登录状态，也 MUST NOT 改变账户状态。失败只驱动两类限流：

- **账户维度**：同一账户连续失败达到阈值（默认 5 次）后，后续登录 MUST 要求提交图形验证码；一次成功登录 MUST 将连续失败计数清零。
- **来源维度**：同一来源在限流窗口内的失败达到上限时，MUST 返回 `429` 并携带 `Retry-After`。来源 MUST 是**客户端 IP**，按下列规则取得：仅当请求来自已登记的代理层时才采信其转发头中的地址；无法确认真实来源时 MUST 按「未知来源」单独计数，MUST NOT 与已解析来源合并，也 MUST NOT 因此跳过限流。IPv6 地址 MUST 按其 `/64` 前缀聚合。来源维度计数 MUST 累计该来源的全部失败且不区分账户，使「单来源撞多个账户」落入同一额度。

部署 MUST 至少登记一个可信代理网段：`wanderchain.auth.trusted-proxies` 为空时应用 MUST 启动失败并给出明确错误，MUST NOT 以「全部请求归入未知来源」的姿态继续提供服务。生产部署 MUST 把前端代理所在网段写入该配置，代理 MUST 原样透传客户端地址转发头。请求来自可信代理时，来源 MUST 取转发头的最后一跳。

#### Scenario: 连续失败后要求图形码

- **WHEN** 同一账户连续失败达到阈值后再次发起登录
- **THEN** 未提交有效图形码时返回 `400` 与 `CAPTCHA_INVALID`，不进行密码比对

#### Scenario: 成功登录后放宽要求

- **WHEN** 账户在触发图形码要求后完成一次成功登录
- **THEN** 连续失败计数清零，再次登录不再要求图形码

#### Scenario: 来源超阈返回 429

- **WHEN** 同一来源在限流窗口内失败次数达到上限
- **THEN** 返回 `429` 并携带 `Retry-After`，且不进行密码比对

#### Scenario: 无法确认真实来源时单独计数

- **WHEN** 请求未经已登记的代理层，或转发头缺失、格式非法
- **THEN** 该请求按「未知来源」单独计数，不与任何已解析来源共享额度，也不被直接放行

#### Scenario: 伪造转发头不扩容额度

- **WHEN** 调用方在直达请求中自行携带转发头、声称来自另一个 IP
- **THEN** 该请求仍按「未知来源」计数，声称的地址不被采信

#### Scenario: IPv6 同前缀共享额度

- **WHEN** 同一 `/64` 前缀下的多个 IPv6 地址连续失败
- **THEN** 它们共用同一来源计数，不因地址变化而重新获得额度

#### Scenario: 单来源撞多账户共用额度

- **WHEN** 同一来源对多个不同账户连续失败
- **THEN** 全部失败计入同一来源计数，达到上限后该来源返回 `429`

#### Scenario: 限流不改变账户状态

- **WHEN** 同一账户连续失败任意次数（含远超阈值）
- **THEN** 账户状态保持原值不变，且仍能以正确凭证登录成功（可能需先通过图形码）

#### Scenario: 空信任边界拒绝启动

- **WHEN** 应用启动时 `wanderchain.auth.trusted-proxies` 为空
- **THEN** 应用启动失败并报出配置错误，不进入可服务状态

#### Scenario: 可信代理按最后一跳识别

- **WHEN** 请求来自已登记的可信代理，且转发头包含多个地址
- **THEN** 以转发头的最后一跳作为来源计数，其余各跳不参与识别
