# 设计：证据账本的方法锚点

## 决策 1：锚点只校验「存在」，不校验「内容对不对」

`ref` 的 `#<anchor>` 只做两件事：在该文件里找得到、找不到就 FAIL。
不解析测试体、不判断断言是否覆盖 Scenario —— 那需要语义理解，闸门做不到，硬做只会产生假阴性。

它堵的是一类具体漏洞：**引用指向真实文件，但其中根本没有对应测试**。
从「一个 156 行的文件」收窄到「一个具体方法」，改名、删方法、换文件都会立刻红。

## 决策 2：只对高风险场景强制，不全量 136 条

全量给 136 个 test 引用补锚点，需要逐个打开文件人工判断「哪个方法对应这条 Scenario」。
错配一个，账本就多一条比现状更糟的假证据 —— 沉默的错误比显式的空白危险。

所以先用 `evidencePolicy.methodAnchorPatterns` 的 5 个关键词（多实例 / 并发 / 重启 / 持久化 / 幂等）
罩住 3 条真正高风险的 Scenario，验证规则可用。全量推进的触发条件留在 `docs/harness-backlog.md` §5。

## 决策 3：不强制证据层级（曾计划，已否决）

初版设想对「多实例」要求 `e2e` 或 `gate`。实测发现：

- `WriteRateLimitInterceptor` 构造注入 `StringRedisTemplate`、实例本身无状态；
- 两个实例共用一个 redis 就是完整的「多实例共享额度」拓扑，单测足以验证。

若硬要求 e2e，只能起两个 Spring 进程或造一个假 e2e —— **规则会逼着人造假**。
同理，「已读与新消息并发不丢」用确定性交错（先塞 6 条、已读推进到第 5 条、断言第 6 条仍未读）
是比真并发更可靠的验证方式。判据只保留「必须有具体方法可指」这一条离散条件。

## 决策 4：补测试而不是把这条件转 deferred

`多实例共用同一额度` 是规格里明写的 Scenario。转 deferred 等于承认它长期没有证据，
而补一条 25 行的用例就能真堵上（`twoInterceptorsShareTheSameQuota`）。
只在补测试成本明显高于延后收益时才转 deferred —— 这里是反过来的。
