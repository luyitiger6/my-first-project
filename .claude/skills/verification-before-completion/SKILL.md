# 先证后宣布

## 何时触发

- 想说「已完成」「已修复」「应该没问题了」
- 想让用户去试一下看看行不行
- 觉得「这次改动很小，不跑也知道没事」

## 铁律

**没有跑过的验证，等于没验证。**

「看起来对」不是证据，「应该能过」不是证据，只有命令输出和退出码是证据。

## 四问自检

在说「完成」之前，逐条回答，答不上来就是没完成：

1. **我实际执行了什么命令？** —— 贴出完整命令，不能只回忆
2. **退出码是多少？** —— 必须是 0，不是「没报错」
3. **输出证明了什么？** —— 指明哪一行输出对应哪个验收标准
4. **有没有我没覆盖的路径？** —— 显式列出未验证的部分

## 本项目的验证顺序

```powershell
# 一步到位：编译 -> 测试 -> 静态红线
powershell -File harness\run-all.ps1
echo $LASTEXITCODE   # 必须是 0
```

分步排查时：

```powershell
powershell -File harness\checks\01-compile.ps1
powershell -File harness\checks\02-test.ps1
powershell -File harness\checks\03-static-guard.ps1
```

## 常见借口与事实

| 借口 | 事实 |
|---|---|
| 「改动很小，不用跑」 | 小改动引入编译错误是最常见的翻车方式 |
| 「测试之前是过的」 | 之前的过与现在的代码无关 |
| 「用户会自己验证」 | 把验证成本转移给用户，等于没做 |
| 「环境问题导致跑不了」 | 先解决环境，不能把不确定当完成 |
| 「只改了注释」 | 注释也可能破坏编译，成本只有 10 秒 |

## 完成声明的标准格式

> 改动：<一句话>
> 验证：`<命令>` 退出码 0
> 证据：<关键输出片段>
> 未覆盖：<显式列出未验证的部分，没有就写「无」>

「未覆盖」这一项不允许省略。诚实地写出没验证的部分，比含糊地宣称全绿有价值得多。

## 与 Harness 的关系

Harness 提供**否决权**，本技能保证**你主动去请求否决**。
两者缺一：没有 Harness，自检只是自我安慰；没有本技能，Harness 会被跳过。

跳过 `harness\run-all.ps1` 的改动，无论看起来多正确，都不算完成。
